# M11 P6: Karma Render Products, Standard Render Vars and Cryptomatte, the remaining details

Package P6 of [M11](M11.md): the details of Karma's product and var nodes that Nova did not render yet. Per-var
sample filters (`driver:parameters:aov:karma:filter`), the missing raw sources, Karma's default value, per-instance
primvar cryptomattes, checkpoint products (`karma:checkpoint`) and deep camera maps (`karma:deep`), on CPU and XPU.
Research: [karma-lops.md](../research/m11/karma-lops.md) (K7), [karma-properties.md](../research/m11/karma-properties.md)
section 3, [karma-aovs.md](../research/m6/karma-aovs.md); Nova's AOV design [M6.md](M6.md) (D9: first hits at the pixel
centre).

Every Karma value below was measured with isolated husk (Karma CPU, Houdini 22.0.466), on scenes built with the actual
LOPs (`tests/husk/karma_products_scenes.py`, checked in as `tests/husk/karma_products/*.usda`) or hand-written probe
scenes of the same geometry. `tests/husk/check_karma_products.py` stores Karma's values and compares Nova's.

## 1. Decisions

| # | Question | Decision |
|---|---|---|
| D1 | Which vars get Karma's sample filters | Every husk var with a `karma:filter` (Karma's LOPs always author one). Vars without one, `["point",{}]` (Nova's own LOPs' and tests' utility vars) and the viewport's Hydra names keep Nova's first hit at the pixel centre (M6 D9): existing outputs stay bit-identical. Karma itself renders `point` as ubox (measured). |
| D2 | Where per-sample values come from | One record per camera sample at its first surface (the hit the cryptomattes take; volumes are transparent to it): mesh, primitive, instance, barycentrics, distance, the first event's distance, the camera ray, the sample's alpha. The CPU wave and the GPU (after the wave's download) record the same data; `accumulateCameraSamples` folds it on the host, so CPU and XPU give the same planes. |
| D3 | Filtered beauty and LPE vars | The beauty (`C.*[LO]`) per sample from the path's radiance and alpha. Other LPE outputs per pass from the change of their film sums (renders with such vars take one sample per pixel per pass). ubox stays the film's ordinary mean. |
| D4 | Per-pixel state | Only planes that ask for it: sums (ubox, accumulate, even/odd), sums and sums of squares (var, mse), value and key (min/max: magnitude; zmin/zmax: camera depth). |
| D5 | Karma's object-coverage modes | As measured: without a var named `PrimId` Karma reports "requires PrimId channel" and averages (ubox); with one, `omin`/`omax` pick the nearest/farthest sample and `idcover`/`ocover`/`edge` still average. Nova does the same and warns once. Unknown minmax modes (`median`, `omedian`) are `min`, as in Karma. |
| D6 | Checkpoints | Nova's own file format (Karma's `scf1` files are its own): the film and the render's progress, written every `saveFrequency` seconds and when the render is stopped, read before the first pass when `resume` is on and the file matches (size, film layout, camera, seed). A finished render removes the file, as Karma. Sample numbers continue from each pixel's count, so a resumed render equals an uninterrupted one. |
| D7 | Deep camera maps | One deep sample per camera sample at its first event (surface, or a volume scatter in front of it), merged with samples within `dcmzbias` while `dcmcompression` > 0 (coverage and colour add, so flattening is exact). Written by the delegate (husk leaves non-raster products to it) as Karma's channel layout with OpenImageIO's deep EXR writer. |
| D8 | Per-instance primvar cryptomattes | As Karma: the gprim's own primvar wins, then the innermost instancer's instance-rate primvar, then outer instancers'; native instances take their roots' constant primvars. |

## 2. Karma's sample filters (measured)

Probe: an orthographic camera over a back plane (two faces, depth 10), a front plane (depth 9) covering 70 % of
column 20, background beyond 30 % of column 30, a tilted ramp; 64 samples, box pixel filter.

| Filter | Karma's result | Nova |
|---|---|---|
| `ubox` | mean over the pixel's samples, misses count 0 (`z` at 30 % coverage: 19/64 x 10 = 2.97); plus the default value | same |
| `accumulate` | sum of the samples (640 = 64 x 10) | same |
| `minmax` `min`, `max` | the sample with the smallest/largest magnitude: \|v\| of scalars (-3 is the maximum of {-3, 1}), the length of vectors ((0, 0, 1) is the maximum of {(0.5, 0.5, 0.5), (0, 0, 1)}); misses count as the default value (min at 30 % coverage: 0) | same |
| `zmin`, `zmax` | the hit sample nearest to / farthest from the camera, misses ignored (zmin at 30 % coverage: 10); no hit: the default value | same |
| `stats` `var` | unbiased sample variance of all samples (misses 0): 21.205 at 30 % coverage | same |
| `stats` `mse` | var / n (0.33133) | same |
| `stats` `even`, `odd` | mean of the even/odd-numbered samples | same |
| `minmax` `last` | the last sample | same |
| `idcover`, `ocover`, `edge`, `omin`, `omax` | without a `PrimId` var: error and ubox; with one: omin = zmin, omax = zmax, the others ubox | same (D5) |
| `median`, `omedian`, unknown | error "Unknown mode", min | same |
| `point`, no filter | ubox | Nova's first hit at the pixel centre (D1) |

The pixel filter distributes the samples (filter importance sampling): with the Gaussian filter a pixel next to an edge
gets samples from beyond it (Karma: 9.84 one column left of the front plane's edge), which Nova does too. LPE vars
take the same filters on their per-sample values (`C` max, var, ...).

Default value (`karma:defaultvalue` 5 on a raw var): ubox adds it to every pixel (15 on a covered pixel, 5 on an empty
one); min/max count misses as it; zmin gives it to pixels without a hit. LPE vars ignore it; `husk:clearValue` does
not change Karma's output at all.

## 3. Raw sources (measured)

| Source | Karma | Nova |
|---|---|---|
| `ray:mask` | 1 per hit sample (ubox: the coverage) | `UtilityKind::Mask` |
| `ray:time` | the sample's shutter position 0..1 (shutter [-0.25, 0.25]: mean 0.5, min 0.004, max 0.997) | `Time` |
| `ray:near`, `ray:far` | the clipping planes along the ray (perspective: near / cos: 0.50206) | `Near`, `Far` |
| `ray:P`, `ray:D` | the camera ray at the lens plane (orthographic: (x, y, 10); perspective: the eye) | `RayOrigin`, `RayDir` |
| `ray:contrib` | the throughput at the hit: 1; 0.5 behind a 50 % opacity sheet (Karma splits the sample) | `Contrib`: 1 (stochastic opacity picks a surface per sample: equal in the mean of opaque scenes) |
| `ray:dPdz` | 0 on surfaces | `DPdz` |
| `ray:hituv` | the face's own parameters (quads: bilinear (u, v)) | `HitUv` (Hydra's quad triangulation mapped back) |
| `ray:hitN_facing`, `ray:hitNg_facing` | normals turned to the viewer | `NFacing`, `NgFacing` |
| `ray:level` | 0 | `Level` |
| `ray:hitstack` | an object index: 1, 2, 3 for the gprims in scene order (moving objects later) | `HitStack`: 1 + the Hydra prim id |
| `ray:pixelsamples` (intrinsic, `max`) | the sample's number + 1 at hits (64 on covered pixels, 0 on empty ones) | `PixelSamples` |
| `ray:noholdout;X`, `ray:holdout;X` | X only on non-holdout / holdout hits | the `holdouts` field of any request |
| `ray:flags`, `stat:cputime`, `stat:indirectraycount`, `oraclevariance` | Karma's internal ray bits and statistics | not filled (warning) |

`karma:dither` only applies when Karma quantizes to 8/16-bit buffers; husk writes the buffers Nova reports (float), so
it changes nothing. `karma:utilitypathexpression` (default `CO`): other expressions record the utility values at a later
path vertex (`C<TG>O`: behind glass; measured: 0.957 x the back plane's depth through a smooth thin glass sheet). Nova
records the camera hit only and warns for other expressions (left open, section 9).

## 4. Per-sample records

`core/integrator/camera_samples.{h,cpp}`: `CameraSampleRecords` (per path slot), `accumulateCameraSamples` and the
shared `UtilityContext::value` (the first-hit AOVs use it too). `Film::wantsSampleRecords()` turns the recording on;
without filtered planes or a deep map nothing changes in the integrator. The GPU writes the records into the wave
(`GpuWave::cryptoInstance`, `camUv`, `camT`, `camEventT`, `camOrg`, `camDir`, `camTime`) next to the cryptomatte's camera
hit, and `GpuRenderer::renderPass` downloads them with the paths' radiance and alpha.

`UtilityRequest` gains `filter`, `defaultValue`, `holdouts` and `index` (an LPE output); `UtilityPlane` gains `aux`
(the second state). `hydra/aov.cpp` reads `karma:filter` (or `filter`) and `karma:defaultvalue`, maps the beauty and
LPE vars with a non-ubox filter and the depth, object id and sample count vars with a filter to utility planes, and
handles the holdout prefixes. `hydra/renderBuffer.cpp` resolves the filter per pixel.

## 5. Checkpoints (measured)

The Karma Render Settings LOP's Checkpointing tab authors a product `checkpoint` with `productType`
`karma:checkpoint`, `productName` (default `$HIP/render/$HIPNAME.$OS.$F4.checkpoint`), custom `bool resume` and
`float saveFrequency`, and a placeholder var `ignored_checkpoint`. husk passes it in the `delegateRenderProducts`
render setting (`-V 4` dumps it). Karma writes its own `scf1` file every saveFrequency seconds and when stopped
(`--timelimit`: "Saved checkpoint"), resumes ("Resuming from checkpoint: 0.6% complete") and deletes it after a
finished render.

Nova (`hydra/products.{h,cpp}`, `renderDelegate.cpp`, `Renderer::saveCheckpoint/loadCheckpoint`,
`Film::save/load`): the file holds a header with a signature (camera matrices, seed), the film (every plane) and the
progress (passes, level, the adaptive oracle's state). The placeholder var is not warned about.

## 6. Deep camera maps (measured)

The LOP's Deep Output tab authors a product `dcm` with `productType` `karma:deep`, `karma:product:dcmcompression` 5,
`dcmofsize` 3, `dcmzbias` 0.001 and the vars of `dcmvars`; the settings carry `karma:global:dcm_usehitdist` and
`dcm_excludeholdouts`. Karma's file: one deep scanline part, channels R, G, B, A, RA, GA, BA (half), Z (float), the
extra vars (float, named by husk name, premultiplied by alpha), ZBack; one sample per camera sample (16 samples per
pixel at 16 spp; 32 behind a 50 % sheet), equal-depth samples with alphas 1/16, 1/15, ... so that compositing them
over gives each its coverage; ZBack = Z on surfaces; compression 10 halves the sample count, 0 and 5 hardly merge;
`dcmofsize` 1 drops RA/GA/BA. Its flattened colour equals the flat image within 0.0076 (A within 8e-5).

Nova writes the same layout (`hydra/deepWriter.{h,cpp}`, OpenImageIO 2.5's deep EXR output from `$HFS`), with R, G, B
as float. Records within zbias merge while compression > 0 (Nova's sample counts are lower on opaque surfaces: one
record per depth); flattening equals Nova's beauty to float precision.

## 7. Per-instance primvar cryptomattes (measured)

Karma Cryptomatte's primvar layers on a point instancer with `primvars:instname` (string, per instance) and
`primvars:piece` (int, per instance), a prototype with its own constant `instname`, a nested instancer and native
instances with constant primvars on their roots: Karma names the instances by the instancer's values (`i1`, `i3`;
ints as `10`..`13`), the prototype's own value wins (`proto_pebble`), the inner instancer of a nested pair wins
(`innerX`/`innerY` over `outerA`/`outerB`), native instances take their roots' values (`native_A`, `native_B`).
Nova: `HdNovaInstancer::ComputeInstanceStrings` flattens string/int instance-rate primvars as the shading ones,
`HdNovaCryptoAttributes` adds them as `CryptoAttribute::perInstance` for names the gprim does not define, and the
cryptomatte accumulation takes the hit's instance (CPU and the GPU's recorded instance).

## 8. Tests

- `tests/test_sample_aovs.cpp` (`[filter]`, `[deep]`, `[checkpoint]`): Karma's filter texts (errors and fallbacks
  included); every filter's arithmetic on a fixed sample sequence (misses, default value, magnitude order of vectors);
  a render over an edge (front 70 %): ubox, zmin, zmax, var, P, object id, mask, sample count, time, near, lens origin,
  the face's (u, v), the beauty's max; LPE planes from the pass sums (accumulate = the film's sum); deep maps
  flattening to the beauty with and without compression (records per depth, the depth var premultiplied); a render
  saved after 5 passes and resumed equals the uninterrupted one bit for bit (beauty, alpha, counts, LPE sums,
  filtered and centre planes, deep records), and a film of another layout or a truncated file is refused.
- `tests/test_gpu_render.cpp` "XPU per-sample AOVs, deep maps and checkpoints" (`[gpu]`): the XPU's filtered planes
  equal the CPU's (the same camera hits), its deep records per pixel likewise, and a checkpoint saved on the XPU
  resumes there to the uninterrupted XPU render bit for bit.
- `husk_karma_products` (`tests/husk/check_karma_products.py`, the LOP-built scenes): 34 planes of `vars.usda`
  against Karma's values (sample filters, raw sources, holdout prefixes, primary samples; fully covered pixels exact,
  edge pixels within the noise of 64 samples), stats even/odd averaging to ubox, Karma's PrimId warning, the
  perspective near/far/origin, the per-instance cryptomatte names of `crypto_instances.usda` at 16 pixels (all as
  Karma's), the deep EXR (hoiiotool reads it as deep, Karma's channel list, flattening to the beauty within 1e-4,
  Karma's depth ranges), and checkpoints through husk (a time limit leaves one, the next render resumes, the
  finished render removes it and equals an uninterrupted render bit for bit).

## 9. Left open

- `karma:utilitypathexpression` other than `CO` (values at later path vertices: needs per-path recording at every
  vertex the expression names, on CPU and XPU); Nova warns and records the camera hit.
- `ray:flags`, `stat:cputime`, `stat:indirectraycount`, `oraclevariance` (Karma's internal ray bits and statistics):
  not filled, with a warning.
- `ray:contrib` behind partly transparent surfaces: Karma splits a sample into weighted hits, Nova's stochastic
  opacity keeps one surface per sample (1); means agree on opaque scenes.
- Deep output: LPE vars other than the beauty, cryptomattes and AO have no per-sample values (warned); volumes deposit
  at the camera path's first event, not as Z/ZBack ranges; camera-visible area lights deposit at infinity. Written
  through husk only (nova_cli writes no non-raster products).
- Checkpoints: the signature covers the camera, seed, size and film layout, not the scene: an edited scene resumes
  from an old file (as Karma, the user deletes it). nova_cli writes none.
- Found while testing (not P6): stochastic opacity hashes the scene's mesh ids (`Scene` filter,
  `hashMix(c.mesh ...)`), which follow Hydra's parallel sync order, so husk renders with partly transparent
  surfaces differ between runs (main before P6 too: 2 of 4 runs differ on the deep scene). A fix (a stable id such
  as the Hydra prim id) changes the images of scenes with opacity and was left for a separate change.
