# M8 design: volumes

Status: binding design for M8. docs/PLAN.md asks for "Volumen: NanoVDB aus Houdini-VDB-Prims, heterogen, Emission/Blackbody, Volume-Light-Sampling", with the result "Pyro-Shots renderbar"; the architecture lists `core/volume/` with "NanoVDB-Grids, Delta/Ratio Tracking, Majorant-Grid, Emission (Pyro: Dichte/Temperatur/Flamme)".

Research, measured on this machine (Houdini 22.0.466, isolated hython/husk only):
- `docs/research/m8/houdini-volumes.md`: what Houdini's LOPs author, what Hydra hands a delegate, how in-memory and file volumes can be read (a probe helper resolved every case), OpenVDB/NanoVDB in Houdini, Karma's volume conventions with calibration renders (`probes/hv_*`);
- `docs/research/m8/volume-algorithms.md`: tracking estimators, majorant grids, spectral tracking, emission, light sampling, NanoVDB, with a prototype that checks every estimator against exact references (`prototypes/va_volume_lab.cpp`, E1-E9).

## 1. Decisions

The user is available but asked to continue under the M3-M10 goal; as in M4 to M7 the research's recommended options were taken where they agree, and D4 resolves where they disagree. The user may revise any of them. The Solaris UI follows Karma's nodes (M6.7).

| # | Question | Decision |
|---|---|---|
| D1 | Data path | **An HDK helper `nova_volume.dll` (`houdini/volume_bridge`)**, built and loaded like `nova_cvex.dll`: hdNova loads it at run time from next to the module. It resolves every field `(filePath, fieldName, fieldIndex, prim type)` through the two C exports of `$HFS/houdini/dso/USD_SopVol.dll` that Karma uses (`SOPgetVDBVolumePrimitiveWithIndex`, `SOPgetHoudiniVolumePrimitive`), so in-memory `op:` volumes (viewport), the USD Render ROP's temp files, USD-ROP-saved `.volumes/` and Volume LOP files all take one path (research H 3.2, 5.1). It converts the result at once to NanoVDB float grids (VDB through `createNanoGrid`; native volumes from the voxel array, exact zeros skipped, voxel centres at integer indices) and returns buffers and index-to-world matrices through an HDK-free C header (`core/volume/bridge.h`, in the style of `core/shading/external.h`). Guards: the exports are checked with `GetProcAddress` (no helper: one warning, volumes stay empty); the returned `GT_Primitive` is never kept; calls are serialized. Fallbacks inside the helper: `.vdb` through `openvdb_sesi` directly if `USD_SopVol` cannot be loaded (plain processes such as `nova_cli`), `.nvdb` through NanoVDB alone (tests). hdNova and core stay HDK-free. |
| D2 | Grids in core | **NanoVDB 32.6 float grids** from `$HFS/toolkit/include/nanovdb` (header-only, Houdini's own library, as PLAN.md's dependency rule asks). Every field is a scalar float grid: vector VDBs (`vel`, `Cd`) are split into three grids by the helper, native vector volumes already arrive as `name.x/.y/.z`. One pointer-free buffer per grid, shared and immutable after loading, uploadable unchanged in M10. Lookups are trilinear (`SampleFromVoxels` order 1), voxel-centred, background (0) outside the active region (Karma, measured H 4.2). |
| D3 | Hydra | The rprim `volume` and the bprims `openvdbAsset`, `houdiniFieldAsset` (warn and skip `field3dAsset`). Field `Sync` reads `filePath`, `fieldName`, `fieldIndex`, `fieldDataType`; loading is lazy, on the volume's sync, of the fields the material reads plus `density` (and `vel` with velocity blur). Volume `Sync`: field descriptors (binding names), material, visibility, transform (motion keys), constant primvars (`karma:object:*`, `nova:object:*`). Bounds come from the grids (the Volume LOP authors no extent). `DirtyParams` on a field (SOP recook: new `&t=`) reloads it. |
| D4 | Volume materials | **Compiled by the existing material pipeline, not fixed-function.** The Karma Pyro Material arrives as a plain MaterialX network of 148 nodes ending in `kma_volume` (H 4.3), which a fixed-function model cannot read; Nova's compiler already lowers those nodes (switches, ranges, `kma_ramp_*`, blackbody, Houdini nodegraphs). New: the `volume` terminal (contexts as for surfaces: nova > kma > mtlx > ""), a `SurfaceModel::Volume` output block (scattering, absorption, emission, anisotropy, secondary anisotropy and mix, Karma's extinction/contribution modifiers and start level) filled by `kma_volume`, `ND_volume` with `anisotropic_vdf` / `absorption_vdf` / `uniform_edf` and their add/mix/multiply forms. Semantics as measured in Karma (H 4.2): coefficients per unit length, σt = σs + σa, emission is radiance per unit length and not scaled by density, HG with g > 0 forward. The algorithm research's objection (the VM provides no majorant) is answered by D7. One scalar program run per tentative collision on the CPU; on the GPU (M10) the same bytecode per thread. A material that binds both a surface and a volume terminal: the volume terminal applies to volume prims, the surface terminal to meshes (Karma never combines them on one prim). |
| D5 | Fields in shaders | **`geompropvalue` / primvar reads on a volume sample the field of that name** at the point (D2 lookup rules). A Primvar leaf of the IR on a volume program is filled from the fields before the code runs, so no new op is needed. Name rules: the binding name or the field name; a width-3 read takes three scalar fields `name.x/.y/.z` (or `name_x/_y/_z`, or the split vector grid); a missing field gives the node's default. |
| D6 | Default volume | A volume without a bound volume material: σs = σt = `density`, white, isotropic, no emission (Karma, measured H 4.2: alpha 0.6321 = 1 - e^-1 through unit density, furnace 0.634 at limit 64). Fast path without the VM. |
| D7 | Majorants | **A dense majorant grid per volume** over the density grid's index space, k = 8 voxels per cell (doubling until at most 128³ cells), each cell covering voxels [lo, lo + k] (trilinear support; research A E2: NanoVDB's node stats are not majorants). Per cell and per field read by the material, the min/max over the covered voxels (dilated by velocity times shutter with velocity blur). The cell's bound on σt and on emission comes from an **interval evaluation of the volume program's bytecode** with those field ranges, the cell's world box for P, and the whole range of the ray globals (`RayType`, `RayDepth`). Rules exist for the ops volume networks use (arithmetic, min/max/clamp, range/remap, pow, exp/log, mix, ramps, switches/ifs, dot/luminance, swizzles/convert, constants, parameters); an op without a rule makes the result unbounded. Unbounded cells fall back to a sampled estimate (max over the cell's voxel and corner evaluations, times 2) with one warning per material; the tracker stays unbiased under such violations (D8). Cells whose emission bound is above 0 get a rate floor of 1/voxel size, so emission without density is still collected (A 4.5). Material edits re-evaluate the intervals (cheap: one interval run per cell); field edits rebuild the ranges. |
| D8 | Tracking | **Spectral tracking with survival biasing** for free flights (A E4 "B3": one common majorant, scatter-or-null choice with throughput-weighted average probabilities, absorption carried as a weight), **ratio tracking** for transmittance (shadow rays, light-only rays, alpha). Emission collected at every tentative collision as beta·ε/σ̄. In-flight roulette when max(beta) falls below 0.1 of its start (survive 0.5). Violation-safe: if σt > σ̄ at a point (D7 fallback cells only), the null coefficient is negative and the choice uses its magnitude (weighted delta tracking): unbiased, more variance; a debug counter reports violations (`TF_DEBUG` `HDNOVA_VOLUME`, tests assert 0 on conservative cells). Overlapping volumes add σ, ε and majorants; a real collision is attributed to volume i with probability σs,i / Σσs for its phase function and tag. |
| D9 | Integrator | A new stage **`traceMedia`** between `intersectRays` and pass A: rays whose segment [0, tHit) overlaps volume bounds (or that are inside an absorbing dielectric) run one flight; a real scatter turns the hit into a **volume hit** (`hitMesh = kVolumeHit`, `hitPrim` = volume id, `hitT` = distance). Area lights crossed before the event are gathered during the flight with the running beta. The dielectrics' Beer absorption moves here and combines multiplicatively. A new pass **C' `shadeVolumes`**: phase function, one light by power (`chooseLight`), MIS with the phase pdf in `bsdfPdf`, continuation from the phase function on `kBsdf`, ray class `Volume`. `traceShadowRays`: unoccluded rays that cross volumes get their ratio-tracked transmittance (also for surface NEE), which multiplies the contribution and the lit LPE parts, not the `unoccluded;` sums. No medium stack: VDB volumes are found geometrically (A 4.7). Scenes without volumes and paths outside absorbing media skip the stage. |
| D10 | Phase function | Henyey-Greenstein, and Karma's secondary lobe (mixture of HG(g) and HG(g2) with `secondarymix`), lobe chosen with the z of the `kBsdf` sample. Karma's extinction/contribution modifiers above the start level are implemented after a Karma probe in M8.3 (their defaults are no-ops; non-default values before then warn once). |
| D11 | Limits, RR, clamp | The `Volume` ray-limit class with its own counter (`eventCounts` widened to 64 bits; per-object `nova:object:volumeLimit`, `karma:object:volumelimit`). Karma's default 0: a volume event spawns a light-only ray, so volumes get single scattering plus the lights seen through the continuation (Karma, measured: furnace 0.388 at limit 0). Russian roulette and the indirect clamp as for surfaces. |
| D12 | LPE and AOVs | Volume scattering is a `V` event; volume emission an `O`-type event with the volume's tag; the scatter class (diffuse or glossy) and Karma's choice for both are probed in M8.3. Alpha: 1 - the mean-channel ratio-tracked transmittance of the camera segment (continued past a real scatter to the segment end), 1 where a surface or a visible light is hit (Karma: only density gives opacity, measured). First-hit AOVs (depth, normal, albedo, ids, utility planes, cryptomatte) are taken from the first surface, volumes are transparent to them; checked against Karma's volume pixels in M8.3 and changed there if Karma differs. |
| D13 | Emissive volumes as lights | `karma:object:treat_as_lightsource` (0 no, 1 yes, 2 auto = when the material emits; Karma's default 0, the Pyro render stage sets 1) and `nova:object:volumeLight` with the same values. A volume light is a `LightType::Volume` entry: power for light selection = 4π · the luminance of Σ emission · cell volume; a point is chosen by a CDF over majorant cells (emission bound per cell) and uniformly inside the cell; the shadow ray ends at the point with ratio-tracked transmittance; MIS against the emission that BSDF/phase continuations collect (A E8: 4-15x more efficient). Karma's `lightsource_diffusescale/specularscale` act as the light's multipliers. |
| D14 | Blackbody | **Karma's measured `ND_blackbody`**: MaterialX chromaticity with a brightness that grows roughly like T⁴ (H 4.4; Nova's luminance-1 lowering would make pyro fire 0.69x dark at 2500 K and 11x bright at 5000 K). A LUT of RGB against temperature measured from Karma (64-128 points, 500-40000 K, linear in 1/T) replaces the lowering for surfaces and volumes (Karma uses the same node in both); negative channels as Karma (unclamped in the node). References that use `blackbody` are regenerated if they change. |
| D15 | Ray globals | Transmittance lookups (shadow rays, ratio tracking) run the program with `RayType` = shadow, so `ray:isshadowray` switches the Pyro Material's shadow colour and intensity; `RayDepth` is the path's event count (`ray:level`). |
| D16 | Settings | Used: `karma:object:volumelimit` (D11), `treat_as_lightsource` and its scales (D13), `vblur`/`volumevblurscale` (D17). Ignored with a reason in the docs: `volumesteprate`, `volumeshadowsteprate`, `volumequality` (Nova does not march; it is unbiased at any setting), `volumesamplingchannel` (majorants come from the material, D7). `volumefilter` other than box/1 warns once and renders trilinear. `volumeuniform` (surfaces as uniform volumes) is deferred. Nova's own: `nova:object:volumeLimit` (exists), `nova:object:volumeLight`. |
| D17 | Motion blur | Transform motion of the volume prim per ray time, as meshes (bounds unioned over the keys). Velocity blur by **lookup offset**: fields are read at x − v(x)·(time − 0.5)·shutter·scale, the majorant cells dilated by max|v|·shutter (Karma XPU's mode; Karma CPU's default "lattice deformation" differs slightly at large velocities: documented). Velocity fields: a split vector grid or `vel.x/.y/.z`. |
| D18 | Determinism | The first exponential of a flight comes from Sobol `bounce(depth, kMedium)` (reserved since M2); the rest of a flight from Nova's PCG `Rng` seeded by hash(pixel seed, sample index, stream); shadow-ray tracking and volume-light points from a new stream block (0x40000). Renders stay independent of the thread count and bit-identical between adaptive and uniform sampling at equal counts. |
| D19 | Velocity blur of geometry (added after M10, section 8) | Meshes, curves, points and point-instancer instances blur by their `velocities`, `accelerations` and `angularVelocities` the way Karma does (measured): **pxr's `HdsiVelocityMotionResolvingSceneIndex`** in Nova's scene index plugin resolves them into time-sampled `points` and instance positions/orientations, which the existing deformation and instancer motion sampling renders unchanged (CPU and XPU alike). **`HdNovaVelocityModeSceneIndex`** before it authors each prim's `__velocityMotionMode` from Karma's `karma:object:vblur` (meshes, curves, points) or `karma:object:instance_vblur` (point instancers): 0 (default) → `ignore` (time samples only), 1 → `noAcceleration`, 2 → `enable`; constant primvars (inherited) win over the render settings' values (int or Karma's menu label); Nova's own `nova:object:velocityBlur` / `instanceVelocityBlur` win over Karma's. Acceleration blur samples the shutter Karma's `geosamples` / `instance_samples` times (default 2: a straight segment between the accelerated ends), `nova:object:accelerationSamples` winning, capped by `nova:maxMotionSteps`; pxr samples accelerations and angular velocities at least 3 times, so a downstream index keeps only shutter open and close where Karma uses two samples. Velocities are per second: the scene globals' `timeCodesPerSecond` comes from `houdini:fps`. `motion:blurScale` and `motion:nonlinearSampleCount` are ignored (as Karma). |

## 2. Scope

### 2.1 M8 delivers

- Volumes in the Solaris viewport and in husk from every source Houdini authors: Volume LOP `.vdb` and `.bgeo.sc`, SOP Import / SOP Create of VDB and native volumes, USD Render ROP temp files, USD-ROP-saved `.volumes/`.
- Heterogeneous scattering, absorption and emission with unbiased tracking on majorant grids; HG phase with Karma's secondary lobe.
- The Karma Pyro Material, `kma_volume` networks and MaterialX volume materials; the default white volume.
- Next-event estimation from volume points, volume shadows on every light sample, MIS; emissive volumes as lights.
- Volume ray limits, Russian roulette, clamp, LPE events, alpha; overlapping volumes, volumes inside and behind glass; transform and velocity motion blur.
- Karma's blackbody.
- The UI in Karma's places (Nova Render Settings: volume limit; Nova geometry settings: volume limit, volume light), and a pyro step in the viewport check.

### 2.2 Deferred

| Item | Goes to |
|---|---|
| Mesh-bounded uniform volumes (`volumeuniform`, fog inside a mesh): they need a medium stack | done in M11 P5 (docs/design/M11-P5.md: media bounded by closed surfaces) |
| Equiangular sampling for point and spot lights in thin media (A E6) | M9 with the light BVH |
| Hero-wavelength spectral MIS for dense chromatic media (A E4) | later optimisation |
| Decomposition/residual tracking for free flights, path guiding | later, if profiles ask |
| Tricubic lookups, volume filters other than box | later (Karma's default is box/trilinear) |
| Karma CPU's lattice-deformation velocity blur | later |
| Cryptomatte ids for volumes | later (D12) |

### 2.3 Deviations from PLAN.md

- The algorithm research proposed a fixed-function volume material; D4 compiles volume networks instead, because the Karma Pyro Material is a MaterialX network. This follows PLAN.md's material pipeline (one IR and bytecode for every material).
- PLAN.md names "NanoVDB aus Houdini-VDB-Prims"; M8 also reads Houdini native volumes (the Pyro Solver's default output, which stays `.bgeo.sc` in husk). An addition, not a change.
- Karma ray-marches with a step rate; Nova tracks unbiased. Karma comparisons use a fine Karma step rate and document the remaining difference.
- Found while building (deviations from Karma, not from PLAN.md): volumes stay transparent to Nova's first-hit AOVs, where Karma averages its sampled volume events into P, distance and N (M8.3 notes); the glass's Beer absorption stayed in pass A (M8.2 notes).

### 3.2 Pass structure per depth

`intersectRays` → `traceMedia` (flights; volume hits; glass Beer; lights crossed inside media) → pass A `gatherLights` (surface hits and escapes; volume hits are listed for C') → pass B → pass C `shadeHits` → pass C' `shadeVolumes` → `traceShadowRays` (Embree occlusion, then transmittance of unoccluded rays through volumes) → AO.

## 5. Risks

| Risk | Mitigation |
|---|---|
| `USD_SopVol`'s exports are undocumented | checked at load, version-pinned; fallbacks `openvdb_sesi` for `.vdb` and the public locked-geometry registry (H 3.3 (ii)) |
| Per-collision program runs are slow for large networks | constant folding removes the interface switches; a fast path for σt = field × constant; batching per tracking step later if the profile asks |
| Interval bounds too loose (ramps, products of fields) | per-cell ranges keep them local; measured majorant/σt ratio in the tests; loose bounds cost time, never bias |
| Large sparse domains | k doubles to keep ≤ 128³ cells (A E1: k = 16-32 costs ≤ 25 % for flights) |
| Heavy tails in dense chromatic media | the indirect clamp as for surfaces; hero MIS later (A E4) |
| Karma's ray-marching bias | references at a fine Karma step rate; residuals documented |
| Denoiser guides in volume pixels | checked in the viewport step of M8.5 |

## 6. Notes as built

Notes on M8.0 as built:
- `core/volume/grid.h`: `VolumeGrid` holds one NanoVDB float grid in a 32-byte aligned buffer (header-only, so the bridge fills grids without nova_core); `VolumeSampler` wraps NanoVDB's trilinear sampler with a per-thread accessor. Vector VDBs arrive as three grids (`name.x/.y/.z` in the volume's field list).
- `core/volume/majorant.{h,cpp}`: the cell layout (k = 8, doubled to at most 128³ cells), a field's support (its stored values dilated by one voxel, per voxel) and per-cell value ranges. Same index space: exact per voxel (voxel v reaches cells floor((v-1)/k) to floor(v/k)); another index space: a leaf at a time, its support mapped as a box. The background is in every cell's range. Root, upper and lower tiles are scattered too (root tiles clamped to the index box).
- `Scene`: `createVolume/updateVolume/updateVolumeMotion/setVolumeVisible/removeVolume`; `commit()` builds the edited volumes in parallel (reference field = density, the default material's majorant = density's cell maximum, world bounds over the shutter sampled 8 times per motion segment), keeps `activeVolumes()` and adds volume bounds to the scene size.
- `houdini/volume_bridge` (`nova_volume.dll`, links GT/GEO/GA/CE/UT/SYS and `openvdb_sesi`; libCE because UT_VoxelArray's headers pull in Houdini's OpenCL wrappers). `USD_SopVol.dll` is found next to the loaded `libUT.dll` (`$HFS/houdini/dso`), loaded with `LOAD_WITH_ALTERED_SEARCH_PATH` so its dependencies come from PATH. Plain processes (tests, `nova_cli`) resolve `.vdb` and `.bgeo.sc` through it as well; `.vdb` falls back to OpenVDB if it returns nothing. A C export `novaVolumeFieldStats` serves the hython test.
- Hydra: `HdNovaField` (openvdbAsset, houdiniFieldAsset; field3dAsset warns) loads lazily per version; `HdNovaVolume` loads the fields it needs (M8.0: density) and places each by its world transform relative to the volume's. **Gotcha:** a field bprim is not re-synced when only an ancestor moves, so the field's world transform is read from the terminal scene index (flattened `xform`) at the volume's sync. **Gotcha:** Hydra dirties a volume on a field edit only through a declared dependency plus a dependency forwarding scene index, which USD adds for Storm only; Nova's scene index plugin now appends `HdNovaVolumeDependencySceneIndex` (volumeFieldBinding depends on each field's volumeField) and `HdDependencyForwardingSceneIndex`. The Hydra test rig inserts both by hand (it runs no renderer plugins).
- Tests: `nova_tests "[volume]"` (trilinear lookups, majorant conservativeness on 400 k points incl. a field at another resolution and offset, scene volumes), `nova_volume_tests` (the bridge on `tests/data/volumes/pyro.vdb`, the research's pyro sim, 585 KB), `nova_hydra_tests "[volume]"` (fields, bounds, transform, visibility, field edits, removal), ctest `houdini_volumes` (in-memory native and VDB fields against Houdini's voxels and transform, a frame change, `.bgeo.sc`, a missing file; husk on a USD-ROP-saved stage loads exactly the three density fields; Hydra in the cooking process loads the `op:` fields and again after a frame change).
- Outside Houdini's bin directory (`nova_cli`, test processes) Windows' own, older `onnxruntime.dll` in System32 was found before Houdini's when the bridge pulled in Houdini's libraries ("The requested API version [20] is not available"); hdNova now preloads Houdini's copy from next to its USD libraries before loading the bridge.
- `nova_cli` sees OpenVDBAsset fields (Pixar's usdVolImaging adapter is a plain plugin) but not HoudiniFieldAsset ones, whose adapter lives in Houdini's HDK plugin `USD_HD.dll`; husk covers those.

Notes on M8.1 as built:
- `core/volume/shader.h`: the volume block (`volume_field`, `VolumeInputs`, kma_volume's defaults); in a material's IR graph the outputs sit at `volume_field::kBase + offset`, and `compile()` splits them into `Program::volume` as it does the displacement. `CompileOptions::volumeParams` folds the material's parameter values into the volume program (`HdNovaMaterial` passes them): it runs per tentative collision and its majorants need the values anyway; a value edit recompiles the material, as every network change does. A new identity in the compiler removes `Select` with a constant condition, so folded switch selectors drop their dead branches and field reads (bit-exact; surface programs shrink too). The recipe-built Karma Pyro Material: 459 instructions + 664 prologue unfolded, 43 (smoke, reads density only) and 67 (fire, density and temperature) folded.
- `core/shading/interval.{h,cpp}`: interval execution of the bytecode with rules for arithmetic, min/max/clamp, mix (corners), smoothstep, select, pow (positive base), exp/log/sqrt, the trigonometric functions, comparisons and logic, dot/length/distance, cross, swizzle/concat, cellnoise, blackbody, RGB↔HSV; anything else, and NaN, is unbounded.

## 8. Velocity blur of geometry (D19, after M10)

Volumes blurred by their velocity fields since M8.4; meshes, curves, points and instances with `velocities` and no time samples rendered sharp. D19 adds their velocity and acceleration blur.

**Karma, measured** (isolated husk, Karma CPU, 256 samples, box filter; quads, points, curves and instances moving 240 units/s, shutter [-0.25, 0.25] frames at 24 time codes per second; alpha profiles along the motion):
- `karma:object:vblur` (int; Karma's registry: 0 No Velocity Blur, the default, 1 Velocity Blur, 2 Acceleration Blur) on the prim, inherited from an ancestor, or on the render settings, where the Karma LOPs author the menu label as a token (`"Velocity Blur"`); a prim's own value wins. Unset: no blur from velocities, time samples still blur. 1: straight motion between shutter open and close, accelerations ignored; time-sampled points then move by their velocities, not their samples. 2: the accelerated positions at `karma:object:geosamples` uniform shutter times (default 2: a straight segment between the accelerated ends; centroid of the test quad 3.501 at 2, 2.018 at 4, 1.936 at 5, 1.868 at 8 samples, against 3.5, 2.019, 1.938, 1.867 for piecewise-linear paths through the samples).
- Point instancers follow `karma:object:instance_vblur` (same values; `instance_samples` for acceleration blur) and ignore `vblur` (Karma warns that it cannot be set per instance). Angular velocities (degrees per second) turn the instances in modes 1 and 2, also without authored orientations.
- Velocities are per second of the stage's `timeCodesPerSecond` (48 halves the blur, `framesPerSecond` changes nothing); husk passes it as `houdini:fps`.
- `motion:blurScale`, `motion:nonlinearSampleCount` and `motion:velocityScale` (UsdGeomMotionAPI) are ignored.

**Design.** pxr's `HdsiVelocityMotionResolvingSceneIndex` (USD 26.05) does the resolving; Houdini registers it for Storm only. Nova's scene index plugin appends three indices before the others (`hydra/velocitySceneIndex.*`):
1. `HdNovaVelocityModeSceneIndex` gives every mesh, curve, point and instancer prim the parameter `__velocityMotionMode` (0 `ignore`, 1 `noAcceleration`, 2 `enable`); to prims with velocity data in mode 2 the primvar `nonlinearSampleCount` (the samples), and to an instancer turning without orientations identity orientations (pxr only turns orientations that exist), single precision (pxr keeps the type: half precision quantized turned instances to about 3e-4 radians), one per instance position (pxr's count check still rejects mismatched angular velocities). Everything is evaluated when read, so edits of the settings re-resolve without rebuilding the chain; an edit of one of the settings' primvars, also on an ancestor, dirties the resolved primvars. The root prim's scene globals get `timeCodesPerSecond` from `houdini:fps`: UsdImaging leaves it out (pxr then uses 24) and Houdini's says 24 whatever the stage has (husk, measured).
2. pxr's index.
3. An index that keeps only shutter open and close of a resolved primvar where Karma uses two samples (velocity blur; acceleration blur at 2 samples): pxr samples accelerations and angular velocities at least three times. Per primvar and only for motion pxr made: points and instance positions need one velocity per element, orientations one angular velocity per element, and pxr's times must differ from its input's. With invalid velocity data pxr passes USD's samples through (Houdini's Motion Blur LOP writes subframe samples exactly at the shutter ends), and orientations sampled over time beside velocities but without angular velocities keep their samples.

The render settings' defaults (`karma:object:vblur`, `instance_vblur`, `geosamples`, `instance_samples`, `houdini:fps`) belong to each render index: the render pass finds its index in its render index's scene index chain (`HdNovaVelocityModeSceneIndex::Find`; two viewers, say Nova CPU and Nova XPU with different render settings, keep their own) and hands them over when the pass is created and on every execute. A change dirties only the prims whose motion it changes: prims with velocity data whose mode changes, whose samples change in acceleration mode, or whose blur depends on a changed frame rate, and volumes (D17) likewise; nothing before anything has resolved (the first sync), so a 25 or 30 fps project costs nothing. The render pass then renders after the next sync. The resolved points and instance transforms are ordinary time samples: `HdNovaSampleVec3fArray` and the instancer's primvar sampling turn them into uniform motion steps (`nova:maxMotionSteps` caps acceleration samples), so the CPU and Nova XPU render them alike and nothing in the core changed.

**Nova vs Karma** (the probes above rendered with both, 256 samples): mean, spread and coverage of every profile agree within the noise (largest band profile difference 0.004-0.013, mean |alpha difference| 0.0002-0.0008) for meshes in all three modes, 2/4/5/8 acceleration samples from the object and the render settings, token-valued render settings, 48 time codes per second, time samples overridden by velocities, points, curves, instance positions and angular velocities (modes 1 and 2, the render settings' `instance_vblur`) and the ignored UsdGeomMotionAPI properties. The shaded reference scene `motion_velocity` (a box, an accelerated arc at 4 samples, points, sheared curves, turning and moving instances, 160x96) matches Karma's reference: means within 0.035 % per channel, no failing block of 960, FLIP 0.0086 against Karma's own 0.0102 between two of its renders. Nova XPU renders `motion_velocity.usda` like the CPU (mean |alpha difference| 4e-5); the reference scenes rendered before stay bit-identical.

**Cost:** the indices evaluate the settings when Hydra reads them, at about 3 µs per prim and sync: 22,500 meshes without velocities sync in 311 ms instead of 254 ms (pxr's index alone 271 ms; the hidden test case "Velocity scene indices add little to the sync" measures it). A first version that looked the settings up once per primvar read cost 750 ms.
