# M10: GPU backend (CUDA wavefront kernels, OptiX acceleration)

PLAN.md: "GPU-Backend: CUDA-Wavefront-Kernels + OptiX-Accel, gleicher Bytecode-Interpreter auf der GPU | XPU-artiger Modus".

Research: `docs/research/m10/optix-accel.md` (OptiX 9.1 acceleration structures, ray queries, motion, filtering, precision, build integration) and `docs/research/m10/cuda-wavefront.md` (kernel decomposition, the bytecode VM on the device, textures, volumes, memory, CPU/GPU agreement, porting order). Both measured on this machine (RTX 5080, sm_120, driver 617.42, CUDA 12.9, OptiX 9.1 headers).

## 1. Decisions

As in M4-M9, the user asked to continue until the renderer is done; the research's recommended options are taken and the user may revise any of them.

| # | Question | Decision |
|---|---|---|
| D1 | Device selection and UI | As Karma CPU / Karma XPU: a second renderer plugin **"Nova XPU"** (`HdNovaXpuRendererPlugin`, the same delegate class with the GPU device) next to "Nova" in the viewport's renderer menu and for husk (`--renderer "Nova XPU"`). The render setting `nova:device` (`cpu` / `xpu`) overrides the plugin's default. Without a usable device (no NVIDIA driver, OptiX ABI too old, out of memory at setup) "Nova XPU" renders on the CPU and warns once. |
| D2 | Modules and build | `core/gpu/` builds a static library `nova_gpu` (CMake CUDA language, MSVC host compiler) when CUDA and the OptiX headers are found (`NOVA_HAS_OPTIX`); hdNova and nova_cli link it. The CUDA runtime is linked statically; the driver (nvcuda) and OptiX (nvoptix) are loaded at run time, as the denoiser does (M7). OptiX device programs are compiled with `nvcc -optix-ir` and embedded in the binary. Flags: `-arch=sm_120` (plus `compute_120` PTX), `-Werror=cross-execution-space-call`, `--fmad=false` (D11); translation units using CUB get `-gencode arch=compute_90,code=sm_120` (CUDA 12.9's CUB does not compile for sm_120 on Windows, research cw 0.12). Since 0.1.3 the kernels are built for sm_75, sm_80 and sm_120 and the programs for compute_75 (section 8). |
| D3 | Shared code | **Per-item kernel bodies** (research cw 9.3): every wavefront pass body becomes a `NOVA_HOST_DEVICE` function over SoA views (`WaveView`, `SceneView`, `MaterialView`, `LpeView`, ...) of plain pointers and counts; the CPU loops over items, the GPU runs one thread per item. Host-only types (`std::vector`, virtual interfaces, OIIO) stay outside the bodies: the accel, the texture sampler and the hit filter become data or function-object parameters. The CPU's images stay **bit-identical** through this refactor (G0). |
| D4 | Device scene | `DeviceScene` mirrors `Scene` after `commit()`: geometry (points, indices, normals, attributes, curves, points, spheres, instances, motion keys), materials (programs, uniforms, closure graphs, texture slots), lights (LightData, the tree, distributions, the alias tables, emissive triangles), LPE tables, volumes (NanoVDB grids, majorants, programs) and textures. Uploads are incremental by object (the scene's dirty sets and versions); all copies go through the backend's own stream (`cuMemcpyHtoDAsync`, research oa 9.4). |
| D5 | Acceleration | OptiX as research oa 12: one compacted GAS per `MeshId` (FAST_TRACE; rebuild on deformation, no refit), one IAS per commit (`instanceId` = MeshId, a per-mesh first-instance table), `OptixSRTMotionTransform` per moving instance (keys repacked), deformation as motion GAS. Hit groups per geometry kind: triangles, round linear and the cubic bases (built-in), built-in spheres (points whose material does not transmit), **custom intersection** for analytic spheres (exit hits for glass), transmitting point spheres and oriented discs. Ray-facing ribbons render as round tubes and ray-facing discs as spheres (OptiX has neither; the same coverage, documented); normal-oriented ribbons are tessellated on the host (4-8 quads per segment) with hits mapped back to (segment, u). Three pipelines: static (single-level instancing), motion, local (subsurface walks on one GAS). Raygen-only queries (`optixTraverse` and hit objects). |
| D6 | Motion interpolation | OptiX interpolates SRT keys by nlerp; Nova's CPU uses slerp. `srtAtTime`/`interpolateSrt` take the backend's rule, so hit reconstruction matches the traversal on each device (0.0012° apart at 10° per key interval, research oa 3.2). |
| D7 | Filtering | Any-hit = Nova's `OpacityFilter::accept` in CUDA (stochastic opacity hash, uniform opacity, the opacity program on the device VM, fake caustics); toggled per mesh by the instance flag `DISABLE_ANYHIT`. Shadow linking: up to 7 categories as visibility-mask bits (2.8x faster than a filter), the rest in any-hit. |
| D8 | Kernels and launches | The passes of the CPU wavefront as kernels (research cw 2.2): generate, intersect (OptiX), media, gather lights, sort (CUB radix sort by material key, fixed capacity), shade (one kernel over the sorted queue, `execute<1>` per lane, uniforms in global memory), walks (OptiX local launch), volumes, shadow (OptiX), emitter emission, flush. Persistent grid-stride kernels with device-side counters (no read-backs inside a wave); OptiX launches at queue capacity with the count on the device. No CUDA graphs around OptiX launches (they failed, research oa 5.4). |
| D9 | Film and AOVs | Per-path accumulators (radiance, alpha, LPE outputs, AO, utility AOVs), flushed once per wave into a device film that each pixel owns (atomics in shading order were 7-65x slower, research cw 6.3). The LPE automaton and its part arena run on the device; first-hit AOVs too; cryptomatte ids are gathered per sample and accumulated on the host. Hydra's render buffers and the OptiX denoiser read the device film. |
| D10 | Textures | Resident MIP chains (research cw 4.5): each texture's levels, read once on the host from the `.tx` files Nova already makes (OIIO), uploaded as CUDA arrays with texture objects in a bindless table; ray-cone footprints pick the level as on the CPU; UDIM tiles are table entries. A device budget (`nova:gpuTextureBudget`, default 50 % of the free memory at setup): above it the finest levels are dropped with a warning; the plan is made over all textures from their shapes before any texel is read, and only the kept levels are read (since R1-48, G7). Demand loading later. |
| D11 | CPU/GPU agreement | The same Sobol and PCG streams: each path makes the same decisions up to floating-point differences. `--fmad=false` everywhere (no measurable cost in the VM probe; 33 % → 2.2 % of differing VM outputs). GPU renders are tested **statistically against CPU renders** with nova_imgcmp's block tests; two GPU renders with one seed are bit-identical. |
| D12 | What stays on the CPU | VEX materials (the CVEX bridge, PLAN.md: "im GPU-Modus wird eine Warnung ausgegeben und ein Fallback-Wert genutzt"): a grey (0.5) diffuse stand-in and one warning per material. Texture conversion, Hydra, scene building, the light tree build, majorant builds. |
| D13 | Volumes | NanoVDB grids on the device (header-only, 32.6), the majorant grids and the volume programs; ratio tracking and free flights as kernels; volume lights, equiangular sampling and emission as on the CPU. |
| D14 | IPR | GAS rebuilds instead of refits (1.4 ms per million triangles), the IAS per commit, uploads by dirty object; the proxy passes, adaptive sampling and the viewport denoiser on device buffers. Target: an edit to the first image under 100 ms on the benchmark scenes. |
| D15 | XPU | "Nova XPU" renders on the GPU; the CPU device is the **fallback** (no device, device lost, out of memory) and runs the CPU renderer with the same settings. Karma XPU renders on GPU and CPU together; with the measured GPU/CPU ratio of 31-68x a CPU share would add 1.5-3 %, so combined rendering is deferred (documented deviation). |
| D16 | Memory | Waves sized to the device: up to 2M paths (1080p at 1 spp) at about 0.7 KB per path plus LPE outputs, smaller when memory is short; volume and walk queues only when the scene has them. Sized from the memory that is free since 0.1.3 (section 8). |

## 2. Scope

### 2.1 M10 delivers

- "Nova XPU": Nova's renderer on the GPU for everything the CPU renders, except VEX materials (D12): meshes, subdivision and displacement (tessellated on the host), curves, points, spheres, instancing, motion blur, depth of field; all native materials and MaterialX graphs through the device VM, textures, ray cones; all lights with the light tree, emissive meshes, light and shadow linking; LPE AOVs, utility AOVs, cryptomatte, AO; volumes; SSS walks, hair; shading queries; opacity and fake caustics; adaptive sampling, IPR, the OptiX denoiser.
- CPU parity tests for every step; benchmarks GPU against CPU.

### 2.2 Deferred

| Item | Goes to |
|---|---|
| Combined GPU + CPU rendering (Karma XPU's device mix) | later (D15) |
| Texture demand loading (tile cache) | later; the budget warns |
| NVRTC compilation of hot shader programs | later (research cw 11.2) |
| Multi-GPU | later |
| Opacity micromaps, cluster acceleration structures, shader execution reordering | later experiments (research oa 13) |

### 2.3 Deviations from PLAN.md

- "XPU-artiger Modus": a GPU device with CPU fallback (D15), not a GPU+CPU device mix.
- The GPU emulates two curve and point styles OptiX lacks (D5): camera-facing ribbons as round tubes, camera-facing discs as spheres; their hits differ in t by up to the radius. Normal-oriented ribbons are tessellated (G6).
- Shading queries (M4) return their defaults on the GPU: a material cannot trace on the device (G6).

### 3.2 Pass structure per depth on the device

generate → intersect (OptiX) → media → gather lights → sort → shade (VM) → walks (OptiX local) → volumes → shadow rays (OptiX) → emitter emission → flush per wave.

## 5. Risks

| Risk | Mitigation |
|---|---|
| The shade kernel's registers and local memory (ClosureList 2.4 KB, SurfaceInputs 1.6 KB) limit occupancy | measure in G2; split into material-evaluation and scatter kernels if needed (research cw 11.1) |
| Interpreter divergence across materials | material sort (measured cheap); NVRTC specialization later |
| OptiX launch overhead (13 µs) on small IPR waves | fewer, larger launches (closest + shadow in one); proxy passes keep waves large |
| Texture memory | the budget (D10) and its warning |
| CPU/GPU differences beyond float rounding | the shared bodies (D3) and statistical tests per step |

## 6. Notes as built

### G0 Shared code

- **Sequencing (deviation from 4):** the pass bodies move into shared headers in the step whose GPU kernel needs them, each move checked for bit-identical CPU images, instead of all of them up front. G0 delivers the foundations every kernel uses.
- `core/scene/hit.h`: `SurfaceHit` and the hit reconstruction of every shape (`resolveMeshHit`: triangles, analytic spheres, curves, points; `meshCurvature`; `instanceToWorld`) as templates over the mesh record type; `Scene::resolveHit`/`curvature` call them with `MeshRecord`. `evaluateCurve` became a template in `curves.h`; `inverseAffine` moved to `motion.h` (no NanoVDB in device headers).
- `core/scene/scene_view.h`: `Span<T>` and `MeshDescView`/`MeshRecordView`, plain arrays with MeshDesc's and MeshRecord's member names. `Hits on scene views equal hits on the records` checks bit-identity on 16 000+ random hits over every shape, style and motion kind.
- `core/integrator/material_lane.h`: the per-hit inputs of shading programs (globals, the tangent frame, primvar fetches) as host+device functions; `fillAndRun` (the CPU's 8/16/32-lane evaluation) calls them.
- `tests/cuda/kernel_headers.cu` compiles the light headers (sampling, the tree, emissive triangles, the light queries of BSDF rays), the subsurface walk, the hit reconstruction on views and the material lane functions as device code. Found on the way: `std::isfinite` in the rect light's spherical sampling, `std::min` in `appendClosure` and `MajorantLayout::index` were not device code.
- The reference scenes render bit-identically before and after (33 scenes, every AOV part, 16 samples; scratch `golden.ps1`).
- **Float-to-int conversions (after M11, bug audit S-1):** a plain cast of a float beyond int's range or of a NaN is undefined, and the devices differ there (x86: INT_MIN; CUDA: the saturated value, 0 for NaN), which D11's "the same decisions" did not cover. Shared code converts with `toInt` (INT_MIN, the CPU's result) or `clampToInt` (`core/math/common.h`): noise cells, the hue sector, octave counts, the volume modifiers' start level. Found by UBSan on the core-only build; the kernels were not compiled or run in that pass.

### G1 First GPU image

- **Files (deviation from 3.1, fewer and flatter):** `core/gpu/` holds the driver loading (`cuda_api`), the device (`device`: primary context, one stream, OptiX context, buffers), the acceleration (`optix_scene`, `programs.cu`), the kernels (`kernels.cu`, their argument and view types in `kernel_types.h`) and the host side of a pass (`gpu_renderer`). They are part of `nova_core` (no separate `nova_gpu` library): the renderer, hdNova and nova_cli get the backend without new link edges. `core/gpu/embed.cmake` embeds the OptiX-IR and the kernel fatbin (sm_120 and compute_120 PTX) as 64-bit words in generated sources (as bytes the 4.5 MB fatbin took MSVC minutes).
- **Shared code (D3, partly):** the per-path steps both devices need moved into `core/integrator/path.h` (the clamp, the surface closure, the receiver kind, where rays leave a hit, the shadow-ray seed, transmitted shadow rays, the roulette probability); the CPU calls them. The GPU's pass bodies mirror `generateCameraRays`, `gatherLights`, `shadeHit` and `traceShadowRays` over these and the G0 headers instead of being the same functions: the CPU bodies are entangled with LPE, volumes, walks and external shading, which arrive on the GPU in later steps. Each later step moves more of a pass into shared code where it pays.
- **Pass:** per wave (up to 2M paths, D16) generate, then per depth closest hits (OptiX raygen over the queue, count on the device), shade (one thread per ray: gather lights, then shade the survivors; atomics append shadow rays and continuations), occlusion (OptiX) and shadow radiance; a flush adds each pixel's samples in order. The host runs maxDepth + 1 depths without read-backs; kernels past a queue's length return. The device film (beauty, alpha, counts) is copied into the host's `Film` after each pass.
- **Materials (G1):** each material's uniform inputs (`MaterialRecord::resolved`) through the shared closure code, so every native surface model with constant inputs renders; the default material reads `displayColor` on the device (its one primvar). Materials with per-hit inputs use their uniform inputs and warn once (G2 brings the VM); graph and VEX materials are grey stand-ins (D12 for VEX).
- **Lights (G1):** the lights before the emissive triangles, chosen by power (`lightTree` is not used yet; G3); volume lights and emissive triangles are not light-sampled, their share of the selection is dropped (unbiased: such emission is found by BSDF rays with weight 1).
- **Renderer:** `RenderSettings::device` (`nova:device` "xpu", `nova_cli --device xpu`) sends full passes to the GPU; adaptive sampling, IPR proxy passes, LPE, utility AOVs and cryptomattes stay on the CPU with a warning per reason, as does everything after a device failure (D15). CPU and GPU passes may alternate: the device film is re-uploaded after a CPU pass. First-hit AOVs come with G4.
- **OptiX tMin:** closest-hit and occlusion queries ignore hits closer than the scene's intersection tolerance. OptiX's triangle test errs by the scale of the triangle's corners, while `offsetRayOrigin` scales with the hit point: on a 2000 x 2000 ground plane seen near the origin, rays leaving the plane found it again and 1/8 of the light was lost (`XPU on a large ground plane`). Embree (exact for the axis-aligned plane) needs no tMin.
- **Results:** `XPU renders the CPU's Cornell box` (default material with displayColor, a Standard Surface metal, glass, a camera-visible rect light; 48x48, 256 samples): 2302 of 2304 pixels within 1e-3 of the CPU's, the means 3e-7 apart (the same Sobol decisions, D11). `XPU white furnace`: 0.99996. Two GPU renders are bit-identical. The reference scenes `mtl_spheres` and `mtl_glass` (1280x640, 256 samples) match the CPU's within 1 % in every pixel; scenes whose materials read primvars (`displayColorLambert`) wait for G2. The CPU's images stay bit-identical (33 reference scenes).

### G2 Materials

- **Device VM:** a material whose inputs vary per hit runs its `Program` per hit on the GPU as `fillAndRun` does per lane: the globals (`material_lane::globalValue`, `instanceToWorld` on the mesh view), the primvars (`primvarValue` on each mesh's attribute bindings, uploaded once per array), then `shading::execute<1>` with the uniform block, its outputs over `MaterialRecord::resolved`. Rows live in local memory (up to 512; larger programs fall back to their uniform inputs with a warning). Closure graphs (`ClosureGraph`, plain arrays) are copied per material, so MaterialX graph closures and surface mixes render; the default material is an ordinary program (its `displayColor` primvar). VEX materials are grey stand-ins (D12).
- **Textures (D10):** `ITextureSampler::textureData` gives a texture's tiles and MIP chains as RGBA floats (Hydra: every level of the prepared `.tx` files through `ImageInput`, the UDIM tiles from `inventory_udim`, the color matrix applied; tests: `MemorySampler`). The GPU keeps them as CUDA mipmapped arrays (half floats when the source has at most 16 bits) and makes a texture object per texture, address modes and filter; a UDIM set is a table of 100 tile objects (1001-1100). The VM's `Tex2D` samples them on the device (`core/gpu/device_texture.h`): hardware trilinear filtering with 8x anisotropy from the ray-cone footprints, `tex2DGrad`; the host's OIIO filters stochastically, so textured images agree statistically (`mtl_textured`: means 0.015 % apart, every 16 x 16 block within 1 %). The budget is half the device memory free at the first upload; beyond it the finest levels are dropped with a warning. `nova:gpuTextureBudget` as a setting comes with G7. (Since R1-48, `textureData` is replaced by `textureInfo` and `textureLevels`, which read only the levels the budget keeps: G7, Texture budget.)
- **Ray cones:** per path as on the CPU (the camera cone of each 32 x 32 tile's center, widened at each scattering event by the curvature and the lobe's roughness); footprints only where the material reads textures or footprint-moved values.
- **Launches by queue length (deviation from D8):** after shading, the three queue lengths come back (12 bytes); the next launches cover exactly the rays there are and a wave ends when none are left. Launching every depth over the full capacity cost 0.3 ms per empty depth, most of a pass at the reference settings' path lengths (5.2 s instead of 1.3 s for 256 passes of `mtl_spheres` at 1280x640).
- **Material sort (deferred within M10):** not done yet. Without it the GPU renders the reference scenes at 1280x640, 256 samples, 10-15x faster than the CPU (CPU 14-31 s, GPU 1.3-2.7 s, 225-370 Mrays/s); a scene with many varying materials decides in G8 whether the sort pays.
- **Results (G2):** 22 of the 33 reference scenes match the CPU in every pixel within 1 %, three more statistically (furnace_rectbox, mtl_normals, mtl_textured); aov_components (LPE) still renders on the CPU (G4); the rest wait for their steps: spheres, points and motion (G6: implicit_spheres*, motion_blur), fake caustics (G6: limits_caustics), volumes (G5: pyro_bare*), VEX (D12: vex_builder).

### G3 Lights

- **Light tree (D11 of M9):** the tree's nodes, trails, lights at infinity, cut and masks are copied per commit (`LightTreeView::lightCount` now gives the per-light arrays' length); `RenderSettings::lightTree` selects it per pass. Light samples pick from it for the receiver at the shading origin with the geometric normal, and BSDF samples weigh lights by its probabilities at the path's MIS vertex (`prevP`, `prevN`, receiver kind and set per path, as on the CPU).
- **Emissive triangles (D14 of M9):** light-sampled like every light; the shadow ray carries the triangle, the barycentrics and the clamp, and the shadow kernel evaluates the material's emission where an unoccluded ray ends (the device VM, as `emitterShadowRadiance`). BSDF hits on them are MIS-weighted with their multipliers, and rays past a limit still collect them.
- **Linking (D15 of M9, D7):** light linking by the receiver set of each instance (the tree's masks, or rejection with the power table); shadow linking by OptiX visibility masks: bit 7 on every instance (unlinked lights), bits 0-6 for the shadow-link categories 0-6 an instance is in; a shadow ray's mask is its light's category bit. Categories beyond the seventh warn and are shadowed by every object (any-hit filtering comes with G6).
- **Dome importance** came with G1 (the distribution is copied with the light). Volume lights wait for G5.
- **Results:** `XPU lights: tree, emissive meshes, linking` (a treated emissive sphere, a light linked to one sphere and shadow-linked to a blocker, a rect light, the tree): every pixel within 1e-3 of the CPU's, the same mean. With the tree on both devices furnace_rectbox and mtl_normals agree in 99.9 % of the pixels within 1 %.

### G4 AOVs

- **First-hit AOVs (deviation from D9):** depth, normal, albedo, the ids and every utility plane except AO come from their own rays through the pixel centers, not from the samples. For GPU passes the CPU still traces them (`renderFirstHits`, renderWave's first part, once per pixel): exact, the same code, and one primary ray per pixel costs little next to a pass.
- **Ambient occlusion:** one ray per camera hit as on the CPU (`stream::kUtilityAo`, below-surface directions occluded), its own queue and occlusion launch after the first depth; per-path counts flushed into a device plane.
- **Cryptomattes (D9):** the GPU records each sample's camera hit (mesh, primitive); after the wave the host adds them with the CPU's `cryptoAccumulate` (`accumulateCrypto`).
- **Light path expressions (D9, D3):** the events, deposits, albedo events, class choice of continuations and light-sample parts moved from wavefront.cpp into `core/integrator/lpe_path.h`, generic over the film and the parts container; the CPU calls them through thin out-of-line wrappers (its images stay bit-identical, aov_components included). `LpeTables::view()` gives them as arrays; the GPU copies the automaton and the tag and output tables when they change. Paths carry their state; light samples' parts (up to 16 states per site) go into a per-wave arena (four parts per shadow ray on average, more are dropped) and the shadow kernel deposits them: plain sums what passes, unoccluded; and shadow;'s lit sums with weight 1, emissive triangles' parts scaled by the emission. One shadow ray per path and depth keeps every pixel's deposits in one thread (atomics come with more samples per wave, G7).
- **Results:** `XPU AOVs: first hit, ambient occlusion, cryptomatte`: the first-hit planes are identical, AO and the cryptomattes' weights agree in every pixel. `XPU light path expressions` (ten expressions with D, G, S, O, A, B events, unoccluded; and shadow;): every output within 0.2 % of the CPU's sum, 95 %+ of the pixels within 1e-3. aov_components' 24 AOVs agree in every pixel within 1 %.
- **Cost:** every pass copies all film planes back (24 AOVs at 320x160 made the GPU slower than the CPU there); G7 copies them when the host reads the film.

### G5 Volumes

- **Shared trackers (D3, D13):** the medium walker, the emission gathering, ratio tracking, free flights, the point query and the span search moved from volume_media.cpp into `core/integrator/medium_track.h`, generic over the scene's volumes (`Media`: active volumes, `MediumVolume` data, transforms, an evaluator) and the lists (the CPU's grow, the GPU's hold 8 volumes along a ray); the volume shader's outputs as a point (`volumePointOf`, the modifiers) are shared too. The CPU's images stay bit-identical. Found on the way: `MajorantDda` keeps a pointer to the layout it starts on, so `MediumVolume` points at the record's layout instead of copying it (a copy left the DDAs reading a dead stack slot: the pyro scenes rendered too dark until the bisection found it).
- **Device volumes:** per volume the majorants (with and without the emission floor), the layout, the light cells, the transform and motion keys, its fields as NanoVDB float grids on the device (each buffer once; NanoVDB's own accessors and trilinear sampler, as on the CPU) and its material's volume shader (code, uniforms, field bindings, defaults, textures). The evaluator mirrors `VolumeEvaluator` (velocity blur, globals, the VM).
- **Passes:** a medium kernel before shading (traceMedia: light crossings with the transmittance in front of each, the free flight or the ratio-tracked light-only segment, the split light transmittance of level-dependent volumes, emission with its LPE events), the gather with the segment weight and crossings, a kernel for the scattering events (shadeVolumes: phase-function light sample, continuation of class Volume, the volume limit), and ratio tracking along unoccluded shadow rays.
- **Volume lights and equiangular sampling (M8 D13, M9 D17):** light samples of volume lights pick a cell and a point as `sampleVolumeLight`; equiangular samples go with the medium kernel, and the free flight's events take their share. A path may now have two shadow rays per depth: each carries its kind, and the shadow kernel runs once per kind, so every path adds at most one contribution per run (deterministic sums without atomics).
- **Results (G5):** pyro_bare and pyro_bare_vl4 match the CPU in every pixel within 1 %; `XPU volumes: media, volume lights, equiangular` (an emissive cube treated as a light, a scattering cube, an equiangular sphere light, the tree): every pixel within 1e-3, the same mean.

### G6 Curves, points, spheres, motion (first part)

- **Geometry kinds (D5):** triangles, round curves of every basis (OptiX's built-in linear, cubic B-spline, Catmull-Rom and Bezier tubes with default end caps), flat ray-facing curves as the round tube of their basis, sphere points and analytic spheres as a custom sphere (the exit when the entry lies behind tmin, as Embree's sphere points; glass needs it), ray-facing discs as the built-in sphere, oriented discs as a custom disc. Each kind is one hit group; an instance's SBT offset is its kind. Hits report the triangle barycentrics, a curve's parameter (Embree's u) or nothing (spheres and points: `hit.h` works from t). Oriented ribbons still wait (tessellation).
- **Motion (D6):** deforming meshes build a motion GAS (one key per step: points, curve radii, sphere radii, custom boxes; the custom intersectors lerp their keys at the ray time), moving instances an SRT motion transform between the IAS and their GAS. Scenes with motion trace with a second pipeline (motion blur on, any graph); static ones keep the single-level pipeline. OptiX interpolates SRT keys by nlerp: `hit.h`'s `motionAt` uses `srtAtTimeNlerp` for records that ask for it (`MeshRecordView::nlerp`), so the GPU reconstructs its hits with the rule its traversal used, and the uploaded keys keep each instance's consecutive rotations in one hemisphere (the shortest arc, as Embree's slerp). The CPU's records keep slerp (bit-identical).
- **Results:** implicit_spheres, implicit_spheres_karma and motion_blur match the CPU in every pixel within 1 %. `XPU curves and points` (every curve basis round, one flat, sphere points, ray-facing and oriented discs): the means 0.1 % apart, 61 % of the pixels within 1e-3 (87 % without the flat curves and ray-facing discs, which the GPU renders as tubes and spheres; the rest differs by the two intersectors' rounding).

### G6 Opacity, fake caustics, subsurface walks, ribbons

- **Opacity any-hit (D7):** filtered meshes (`Scene::OpacityFilter`'s: opacity, fake caustics, shadow-link categories past the seventh) get a second hit group per kind with `__anyhit__filter`, which makes the CPU filter's decision (`core/gpu/device_shading.h`'s `acceptHit`): fake-caustic objects are skipped by shadow rays, categories past the masks tested per instance, and a partly opaque hit kept with probability `opacity` by the same hash of (ray seed, the mesh's stable key, primitive, instance). The opacity program runs in the any-hit program on the device VM (`runMaterialProgram`, shared with the shading kernels). Rays carry their opacity seeds when some mesh is filtered.
- **Fake caustics (M4 3.3):** the shading mirrors the CPU's (after a diffuse event glossy lobes are dropped and transmission becomes a pass-through with the transmittance; light-only rays cross fake-caustic objects). Shadow rays take the second phase of `fakeCausticTransmittance` as launches: after the occlusion test the unoccluded rays start a queue, and per crossing (at most 8) a closest-hit launch and a kernel that ends the ray, blocks it, or multiplies the surface's `closureTransmittance` in and moves it past the surface. The queue length comes back after each crossing, so the loop ends when no ray is left. The buffers exist only when the scene has fake caustics.
- **Subsurface walks (M9, deviation from D5's local pipeline):** a walk is a third raygen in the existing pipelines, not a pipeline of its own: they also trace single GASes (`ALLOW_SINGLE_GAS`), and the walk takes its segments into the instance's object space and traverses that mesh's GAS alone with its unfiltered hit group (as `Scene::intersectLocal`; cut-outs do not stop a walk). The custom intersectors read the mesh from the one payload value there, since a GAS traced alone has no instance id. The shading queues the walks; the raygen runs `randomWalk` from `subsurface.h` unchanged with the same Sobol and Rng streams; an exit kernel shades the exit as `walkSubsurface` (Lambert light sample on `walkLight`, cosine continuation of class SSS). The exit's shadow ray is a third kind (the shadow kernel runs once more), so the shadow queue holds three rays per path in scenes with walks. Whether a scene can walk is decided from its materials (a native model with a subsurface weight or a program writing it, graphs with a subsurface leaf or a native segment); a walk elsewhere is counted, ends its path in that pass, and the next pass makes room.
- **Normal-oriented ribbons (D5):** tessellated on the host, 8 quads per segment (4 above 262 144 segments), spanned across the normal interpolated on the basis at half-width the radius, one point set per motion step. The closest-hit, any-hit and walk programs map a triangle hit back to the segment and its parameter (`ribbonHit`), so `resolveCurveHit` reconstructs it as Embree's ribbon hit. Oriented curves Embree draws flat (linear, or without normals) are ray-facing and render as round tubes.
- **Shading queries:** the GPU's VM returns the queries' defaults (no traces from inside a material on the device); scenes whose materials query render them on the GPU with those defaults (deviation, 2.3).
- **Results:** `XPU opacity` (a checker cut-out by an opacity program, a half-transparent sphere, their shadows), `XPU fake caustics` (a solid glass ball and a tinted thin-walled pane over a diffuse ground) and `XPU subsurface walks` (a sphere with a chromatic mean free path, a scaled box instance): every pixel within 1e-3 of the CPU's, the same means. limits_caustics (27 % in its worst block before) and furnace_materials match the CPU in every pixel within 1 %. `XPU oriented ribbons` (twisting blades of the three cubic bases, one deforming): 74 % of the pixels within 1e-3 (the rest along the edges and twists, where the quads leave Embree's exact ribbon), the means 0.05 % apart. The CPU's images stay bit-identical (33 reference scenes); the full `ctest` passes.

### G7 Hydra and IPR

- **Nova XPU (D1):** a second renderer plugin, `HdNovaXpuRendererPlugin` ("Nova XPU" in the viewport's renderer menu, `husk --renderer "Nova XPU"`): the same delegate with the GPU as its default device. `nova:device` (cpu, xpu) overrides it; it is on the Render Settings LOP's Nova tab but not authored by the Nova LOPs (`hda: false` in `nova_settings.json`), so the renderer the user picks decides. As Karma XPU it has a viewport parameter file of its own (`HdNovaXpuRendererPlugin_Viewport.ds`); the scene index plugins (implicit surfaces, light linking) are registered for both renderers. Without a usable GPU it renders on the CPU and says so once.
- **Rendering Engine (Karma-like UI):** the Nova LOPs' header has a Rendering Engine menu (CPU, XPU) where the Karma LOPs have their engine menu. It authors `husk:default_delegate` on the settings prim, as Karma's does, and picks the renderer of the USD Render ROP inside the Nova LOP and of Nova (Setup). The viewport renders with the renderer chosen in its own menu.
- **Proxy passes and adaptive sampling:** a pass over selected pixels (one per stride x stride block in IPR proxy passes, those below the maximum, those the variance oracle keeps) selects them once for both devices (`Renderer::selectPixels`); the GPU gets them as a list and the generation kernel reads each path's film pixel from it, the first-hit AOVs come from the CPU for the listed pixels. Nothing in a pass falls back to the CPU any more.
- **Uploads by dirty object (D4, D14):** `MeshRecord::geometryVersion` changes with every `updateMesh` (unique in the process). The GAS (with its build inputs and custom primitive data) and the geometry arrays on the device (points, indices, normals, curves, radii and the attributes materials read from the description) of a mesh whose version and filtering stay are kept; instances, the IAS, materials, lights and the tables are uploaded per scene version. `XPU edit latency` (4.2M triangles, 640x360): the first pass 183 ms, a pass after an edit of a light, a material or a transform 7 ms (52 ms with every GAS rebuilt; a pass alone takes 2 ms). `XPU incremental scene updates`: after edits of geometry, a transform, a material with opacity (the mesh becomes filtered) and a removal, a renderer that saw every version renders a fresh renderer's image bit for bit.
- **Film read-back (D9):** the host keeps the counts itself (each rendered pixel gets `spp` more); the sums (beauty, alpha, AO, LPE outputs) stay on the device until something reads the film (`Renderer::film()`, an adaptive checkpoint, a CPU pass). After GPU passes Hydra copies the beauty, like the other AOVs (M6 D11), only when a reader mapped it since its last copy and at the end; after CPU passes it still copies the beauty every pass.
- **Texture budget (D10):** `nova:gpuTextureBudget` (MB; 0: half the memory free at the first texture upload), on the Advanced tab's Textures.
- **Texture budget planned before reading (R1-48, after M10):** `textureData` read every UDIM tile's every level as float RGBA into host memory before the budget dropped levels (8 tiles of 8K: 11.9 GB). Now `ITextureSampler::textureInfo` gives each texture's tiles and stored levels from the files' headers, and the GPU plans the budget over every texture the scene's materials sample (`core/texture/texture_budget.h`) before any texel is read: if everything fits, every tile keeps all its stored levels (the device data are bit-identical to before); otherwise the textures are capped at the largest power-of-two size that fits (finer levels dropped, smaller textures untouched), then, in order of first use, a reduced texture gets one level more while that fits, all tiles of a UDIM set together (no resolution seams between tiles). `textureLevels` reads only the kept levels of one tile, a band of 64 rows at a time (OIIO tiles or scanlines), converts each band to half and the GPU copies it into the CUDA array at once; a file without stored MIP levels (read directly, `nova:textureAutoTx` off) gets a kept coarser level made by a box filter while its finest level streams by once (before, such a file was uploaded whole whatever the budget). Host memory is a band and a row of sums. The previous policy dropped levels per tile in the order of first upload, so the first textures kept everything and later ones could end at 1 x 1; for a single texture both policies keep the same levels. The plan covers exactly the textures the device samples, by the rule the upload follows (surface programs and per-hit opacity programs that run on the GPU, volume shaders within its rows; not VEX stand-ins or programs over the GPU's rows, whose textures are not uploaded either). The default budget is measured when the first texture loads, not at a first scene without textures. In IPR the plan is made with every scene version and with every change of `nova:gpuTextureBudget` (then without a scene edit, and nothing is uploaded if the new plan keeps the same levels); a device copy stays while it holds what the plan keeps, unused ones while they leave room, and only the textures whose kept levels change are read again, so the device holds what a fresh render would. Measured with nova_cli on Nova XPU (8 UDIM tiles of 8192^2 half RGB `.tx`, 5.3 GB on the device, default budget): peak working set 11.9 GB before, 0.50 GB after (0.42 GB for a scene without textures), 13.7 s and 12.1 s, images bit-identical; with a 1000 MB budget 0.49 GB and 1.2 s (only the 2048^2 levels are read; before 11.9 GB and 10.2 s).
- **Denoiser (deviation from D9, D14):** the OptiX denoiser keeps working on the host's buffers (M7); the film comes back for it, in the viewport at most every 50 ms.
- **Results:** `XPU proxy passes and adaptive sampling` (Cornell box, two proxy levels, 128 samples; then with the variance oracle): the same counts in every pixel, 99.96 % (proxy) and 100 % (adaptive) of the pixels within 1e-3 of the CPU's. mtl_spheres at 1280x640 with 256 samples through nova_cli: 1.25 s (296 Mrays/s). The Solaris UI test renders its stage with husk and Nova XPU (on the RTX 5080).
- **Viewport check** (`run_viewport_check.ps1 -Only xpu`, its own Houdini instance with the staged package): Nova XPU is in the renderer menu next to Nova (now labelled Nova CPU, as Karma CPU), Karma CPU and Karma XPU; with the Nova LOP set to XPU and 100 000 samples the viewport shows the render progressing (2460 samples after 2.5 s in the viewport's statistics) through the map-driven beauty copies; a prim added live appears; the image matches Nova on the CPU (means 0.575, 0.581, 0.6015 on both). The Rendering Engine menu sits under the resolution, where the Karma LOP has its engine menu.

- **The viewport while the camera moves (fixed after M10):** every restart cleared the render buffers, and the next frame's restart interrupted the first pass, so the viewport showed nothing until the motion stopped. The buffers now keep the last image until the restart's first pass replaces it (they are cleared only for new buffers or a new size), and the first proxy pass after a restart is never interrupted (it is short by design; `Renderer::firstProxyPass`). `run_viewport_check.ps1 -Only tumble` turns the camera every 40 ms: the grabs during the motion show the scene (Nova CPU and Nova XPU; before the fix only the background). The viewport menu says Nova CPU and Nova XPU, as Karma CPU and Karma XPU.

### G8 Closing

- **Fallback and failover (D15):** without a usable device (no driver, OptiX too old, out of memory at setup, or `NOVA_XPU_DISABLE` set) Nova XPU renders on the CPU and says so once; a device error during a pass sends that pass and the rest of the render to the CPU, and the film starts over if the device held sums the host lacked. `XPU falls back to the CPU` (with `NOVA_XPU_DISABLE`) renders the CPU's image bit for bit. It found a crash: the destructors of a device that never initialized called the CUDA API through a null table (a machine without an NVIDIA driver would have crashed as Nova XPU fell back); `Device::Scope` now makes no context current without one.
- **Material sort (D8): not done.** `XPU material divergence` (64 spheres with 64 different per-hit programs of both native models, against the same scene with one program, 960x540, a dome): 3.85 ms per pass in both. Camera rays hit objects in coherent blocks, and the divergence of scattered rays does not show next to traversal and the per-depth launches; the CUB sort and its extra launches would cost more than they save here. It stays an option for a scene that shows the cost.
- **Not on the GPU (documented):** VEX materials (grey stand-ins, D12), shading queries inside materials (their defaults, G6), the denoiser on device buffers (G7), combined GPU + CPU rendering (D15), demand-loaded textures (2.2).

## 7. M10 closing

M10 delivers PLAN.md's "GPU-Backend: CUDA-Wavefront-Kernels + OptiX-Accel, gleicher Bytecode-Interpreter auf der GPU" with the result "XPU-artiger Modus":
- **Nova XPU** (G1, G7): a second renderer, "Nova XPU", in the viewport's menu and for husk, the Nova LOPs' Rendering Engine menu as Karma's, `nova:device`; the CPU is its fallback (G8).
- **The same renderer on the device** (G0-G6): the wavefront passes as CUDA kernels over the shared headers (path steps, hit reconstruction, light sampling and the tree, the material lanes, LPE, the medium trackers, the random walk), the bytecode VM with textures on the device, OptiX for every geometry kind (triangles, curves of every basis, ribbons tessellated, spheres, points, discs, motion), the any-hit filter, fake caustics, volumes, SSS. With the same Sobol and Rng streams every path makes the CPU's decisions: the reference scenes agree with the CPU in every pixel within 1 % (textures statistically), the unit tests mostly within 1e-3 per pixel, and two GPU renders are bit-identical.
- **IPR** (G7): proxy passes and adaptive sampling on the device, uploads by changed mesh (an edit of a 4.2M-triangle scene shows in 7 ms), the film read back only when read.
- **The CPU unchanged:** its images stayed bit-identical through every refactor into shared code (33 reference scenes, every AOV part).

Deviations:

| Step | Deviation |
|---|---|
| G0 | The pass bodies moved into shared headers step by step, as each GPU kernel needed them, not all up front; the GPU's passes mirror the CPU's over them instead of being the same functions. |
| G1 | Files fewer and flatter than 3.1 (`core/gpu/`, part of `nova_core`). |
| G2 | Launches sized by queue lengths read back per depth, not persistent kernels at capacity (D8). |
| G4 | First-hit AOVs come from the CPU (one ray per pixel), not from device samples (D9). |
| G6 | Subsurface walks are a third raygen of the two pipelines, not a local pipeline (D5). Shading queries return their defaults on the GPU. Ray-facing ribbons and discs render as round tubes and spheres (D5). |
| G7 | The OptiX denoiser works on host buffers (D9, D14). After GPU passes Hydra copies the beauty when a reader maps it, not every pass. |
| G8 | No material sort (D8): measured without effect. |

Performance (docs/benchmarks.md, M10): per sample Nova XPU on an RTX 5080 renders the reference scenes 9-16x faster than Nova on the 16 threads of a Ryzen 7 9800X3D (volumes and heavy layered materials 4x), after a setup of 0.26-0.42 s per render; at 960x540 with 64 samples, the setup included, 4.3-7.7x (volumes 1.9x). The research's probes reached 31-68x: the shade kernel takes 89.5 % of the GPU time (217 registers, a 16.7 KB stack per thread; capping the registers made it slower), so splitting it into material evaluation and scattering (risk table, research cw 11.1) is the later work.

Left for later:
- combined GPU + CPU rendering, multi-GPU; demand-loaded textures; the denoiser on device buffers;
- shading queries and VEX materials on the device; NVRTC specialization of hot programs;
- the shade kernel split into material evaluation and scattering (the GPU's main cost); the volume kernels' speed; opacity micromaps, shader execution reordering.

## 8. After M10: NVIDIA GPUs before the RTX 50 series (0.1.3)

M10 built the device code for `sm_120` alone, so Nova XPU ran on the RTX 50 series and fell back to the CPU everywhere else (the kernel module did not load). This section widens it to every GPU that the driver OptiX 9.1 needs supports. It is developed on the one GPU of this machine, an RTX 5080: what could be checked there is checked, what needs another card is named in 8.4.

### 8.1 What decides which GPUs can run Nova XPU

- **OptiX 9.1 (ABI 118) needs NVIDIA driver 590 or newer** (NVIDIA's release announcement and download page). The 590 branch supports Turing and newer only: the 580 branch is the last for Maxwell, Pascal and Volta (GTX 900, GTX 10 series). So the oldest architecture worth building for is **compute capability 7.5** (Turing: RTX 20, GTX 16, Quadro RTX, T4).
- **nvcc compiles the two groups with different compilers.** From CUDA 12.8 on, compute capabilities 10.0 and greater use an NVVM IR dialect based on LLVM 18 that "differs from the older dialect used for pre-Blackwell architectures" (CUDA 12.8 features archive). Measured with CUDA 12.9 on `core/gpu/kernels.cu`: for `compute_120` the PTX has 64 functions in 18.0 MB, for `compute_75` 46 functions in 27.3 MB (it inlines more); the code for `sm_120` is 18.1 MB from the first and 26.9 MB from the second; `ptxas` takes about 3 minutes for the first and 7 for the second, per architecture. GPUs before the RTX 50 series therefore run other machine code from the same source.
- **Code for X.y runs on every X.z with z >= y** (CUDA's binary compatibility), so code for `sm_80` serves Ampere and Ada (RTX 30: 8.6, RTX 40: 8.9).
- **Without code for its architecture the driver compiles PTX when the module loads.** Measured on the RTX 5080 with a fatbin of `compute_75` PTX alone and the driver's cache off: `cuModuleLoadData` took **336 s**. With code it takes 5.5 s the first time and 0.03 s from the driver's cache.
- **OptiX compiles its programs for the device itself** (research oa 9: "compute_75 is enough"): one OptiX-IR serves every GPU.
- **The kernels' stacks grow with the GPU.** The driver allocates local memory at the first launch for every thread the device can run at once. Measured on the RTX 5080 (84 multiprocessors): the free memory falls by 1.98 GB with the `compute_120` kernels and by 2.33 GB with the `compute_75` kernels (23.5 and 27.7 MB per multiprocessor), a 160x80 film and a 9 MB wave included.

### 8.2 Decisions

| # | Topic | Decision |
|---|---|---|
| E1 | Supported GPUs | Compute capability 7.5 and newer with driver 590 or newer. `Device::init` reads the capability and refuses an older GPU by name before OptiX is asked; an OptiX ABI error names the driver version needed. Either way Nova XPU renders on the CPU and says why (D15). |
| E2 | Kernels | One fatbin, built by one nvcc call (`--threads 0`): for the architectures below 10.0 the PTX of `compute_75` and code for `sm_75` and `sm_80`; for those from 10.0 on the PTX of `compute_120` and code for `sm_120`. The driver takes what fits the device. `NOVA_GPU_ARCHS` (CMake cache, `75;80;120`) names the architectures; its smallest is the oldest GPU that runs. A shorter list is a development build (`120`: half the build time); `tools/installer/build.ps1` refuses to package one. |
| E3 | Architectures without code | Hopper (9.0), data-centre Blackwell (10.0) and architectures after 12.x get the driver's compile of their group's PTX: minutes, once per driver, with a message before the module loads. Not built ahead: there is no such card to check the code on, and each architecture adds about 7 MB and 7 minutes. |
| E4 | OptiX programs | Built for `compute_75`, the oldest architecture, for every GPU. |
| E5 | Device choice | The driver's first device (its fastest, by the driver's default order). `NOVA_XPU_DEVICE=<index>` names another; an index the driver lacks is refused by name. Still one GPU per render (2.2). |
| E6 | Memory (replaces D16's fixed wave) | The most paths of a wave are planned at the first pass and when what a wave holds changes: a 4096-path wave is reserved to measure the bytes per path (777 B for surfaces alone, more with light path expressions, media, fake caustics, guiding), then the waves get half of the memory that is free after setting aside 32 MB per multiprocessor for the kernels' stacks, between 64k and 2M paths. A reservation that still fails for lack of memory is repeated with half the paths. A wave holds whole pixels and each pixel owns its sums, so the image does not depend on the wave's size. `NOVA_XPU_MEMORY_MB` plans textures and waves as on a card that had only that much free. |
| E7 | Tests | The tests' build assembles the `compute_75` PTX for the test machine's GPU (`nova_gpu_kernels_old`, `NOVA_GPU_CHECK_ARCH`); `GpuRenderer::setKernelImage` loads it in place of the embedded kernels. One test renders with both and compares bit for bit; ctest's `xpu_older_architecture_kernels` runs every GPU test on it. |
| E9 | Experimental until tested (user decision, 2026-11-11) | Nova XPU has run on `sm_120` only (`NOVA_GPU_ARCHS_TESTED` in `core/CMakeLists.txt`). A GPU that runs the code of no tested architecture is experimental (`Device::support`): `Device::init` refuses it with the way to turn it on, and Nova XPU renders on the CPU; with `NOVA_XPU_EXPERIMENTAL_GPUS` set (not empty, not 0) it renders on the GPU and its message says experimental. The installer sets the variable in Houdini's package file: its Graphics row asks the CUDA driver for the first device's compute capability, as the renderer does, and shows a check box for an experimental card (off by default; kept across updates; `--experimental-gpus` and `--no-experimental-gpus` on the command line). An architecture leaves the experimental state by being added to `NOVA_GPU_ARCHS_TESTED` once Nova XPU is checked on such a card. |
| E8 | AMD and Intel GPUs | Not part of this step: neither has CUDA or OptiX, so each needs a backend of its own (8.5). They render on the CPU. |

### 8.3 Checked on the RTX 5080

- **The older group's kernels, assembled for `sm_120`, render the same images bit for bit** as the `compute_120` kernels: 7 reference scenes at 1280x720 with 256 samples (materials, the Cornell box, fog, pyro, the material furnace, the atmosphere), the test `XPU kernels of the older architectures render the same image` (surfaces, a medium, subsurface walks, light path expressions; float sums), and **all 60 GPU test cases** pass on them (`xpu_older_architecture_kernels`). `--fmad=false` and IEEE arithmetic make the two compilers agree. Speed: within 2 % on those scenes (mtl_spheres 178.6 against 181.6 Mrays/s, cornell_rect 146.6 against 149.7, fogbox 59.2 against 59.3).
- **The OptiX programs built for `compute_75`** render 10 reference scenes bit for bit as those built for `compute_120`, at the same speed; OptiX compiles the module in 2.2 s at its first use and caches it.
- **Smaller waves:** `XPU renders in smaller waves when memory is short` renders 82944 pixels in waves of 65536 paths (`NOVA_XPU_MEMORY_MB=1`) and in one wave: the same sums bit for bit, light path expressions included. `XPU halves its waves when the device runs out of memory` makes buffers above 16 MB fail (`Device::setAllocationLimit`): the pass goes on with waves of 73728 paths and the same sums. The 36 reference scenes at 640x360 (`tests/stress/ab_builds.py --new-env`): with `NOVA_XPU_MEMORY_MB=1` 33 are identical and the three with large textures differ, because the cap also shrinks the texture budget (finer MIP levels are left out, as documented); with 3200 MB, room for the textures and waves of 124854 paths, those and the other textured scenes are identical too.
- **Against 0.1.2:** all 36 reference scenes render bit for bit as the release's build on the RTX 5080 (16 samples; 19.8 s against 18.1 s over the scenes): its kernels are the same code, and the programs' new OptiX-IR changes no pixel.
- **The fatbin** holds PTX for `sm_75` and `sm_120` and code for `sm_75`, `sm_80`, `sm_120` (cuobjdump): 31.3 MB against 10.3 MB before, so `hdNova.dll` grows from 45.9 to 66.9 MB. It builds in 7.6 minutes (4 before).
- **Experimental cards (E9):** `XPU on an untested GPU architecture is experimental` lets the device report 8.6 and 6.1: refused with the way to turn it on and rendered on the CPU without `NOVA_XPU_EXPERIMENTAL_GPUS`, rendered on the GPU and marked experimental with it, too old either way at 6.1. The installer's 12 unit tests cover the same rule, the package file and the manifest; silent installs in a temporary folder turn the option on, keep it across an update and turn it off.
- **The whole suite:** ctest 728/728 (`reference_cli_karma_atmosphere` skipped by design), with the five new GPU test cases and `xpu_older_architecture_kernels`.

### 8.4 Not checked: needs another card

- No Nova XPU render has run on an RTX 20, 30 or 40 or on a GTX 16. The code `ptxas` wrote for `sm_75` and `sm_80` has never been executed; what ran here is the same PTX assembled for `sm_120`.
- OptiX on those cards (the GTX 16 series traces without RT cores), their speed, and their memory use: the stack reserve of 32 MB per multiprocessor is measured on `sm_120` only.
- The message for an older driver: no such driver here to raise it. (The branches for an older GPU and for an experimental one run in `XPU on an untested GPU architecture is experimental`, where the device reports 6.1 and 8.6 through `Device::setCapabilityOverride`.)
- The installer's check box in the real window: this machine's card is a tested one, so the window shows none. Its states are checked against the interface's mock backend (`?oldgpu`, `?ancient`, `?nodriver`), the option itself through silent installs (`--experimental-gpus`), and Houdini reads the package file it writes (an isolated hython sees the variable in its C runtime environment).
- The driver's compile for an architecture without code is measured on `sm_120` (336 s), not on `sm_90` or `sm_100`.

### 8.5 AMD GPUs: what a backend would take

AMD GPUs run neither CUDA nor OptiX. The path other renderers take is HIP for the kernels and HIP RT for ray tracing:
- **HIP SDK for Windows** officially supports Radeon RX 7000 and RX 9000, Radeon PRO W7000 and the AI PRO R9700 on Windows 11; RDNA 2 and older are listed as not supported (AMD's system requirements page, read 2026-11-11).
- **HIP RT** (3.x) has triangles, custom primitives with intersection functions, multi-level instancing, motion blur and ray masks, with hardware ray tracing on RDNA 2 and newer (GPUOpen's page). Its feature list names no curves or spheres: Nova's curve bases and spheres would need intersectors of their own. Its SDK licence allows shipping the library with a product.
- **The work:** the kernels' source is shared CUDA C++ and for the most part portable to HIP; `programs.cu` (ray generation with hit objects, the any-hit filter, the walk pipeline), `optix_scene.cpp` (acceleration structures, motion, compaction) and the texture objects are OptiX and CUDA driver code and would be written again for HIP RT. That is a milestone of M10's kind (G0 to G8), and it needs an AMD GPU to run and test on, which this machine does not have.
- PLAN.md names "NVIDIA RTX" and "CUDA/OptiX" for the GPU: an AMD backend is an extension of the plan and gets its own research and design note first.
