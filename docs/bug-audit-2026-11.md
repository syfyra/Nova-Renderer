# Bug audit, November 2026

After M10 a multi-agent audit read the whole tree slice by slice (16 subsystem finders plus cross-cutting lenses: CPU/GPU parity, concurrency, memory and lifetime, numerics, error paths, recent code). Every finding was verified adversarially before it counted: 72 unique findings, 71 confirmed, 1 rejected (R1-57: VEX surfaces get the shutter time as `Time` by design). The fixes were made per file cluster, then reviewed independently against the pre-fix tree; the review found 8 problems in the fixes themselves, all corrected (section 2).

State after the fixes: ctest 500/500 (46 new tests), 28 `[gpu]` test cases, installer `cargo test` 7/7. The golden CPU hashes changed in 4 of 33 reference scenes, each explained: `mtl_diffuse` (R1-23, rough diffuse rims), `mtl_graphs` (R1-25, lobe picks of mixed materials: same mean, other noise), and `limits_caustics` / `aov_components` (R1-1; an A/B build with the old MIS origin reproduced the old hashes exactly; `aov_components` moved in the last bit on 18 pixels, `limits_caustics` by -0.044 % behind its fake-caustic object, toward Karma). All Karma reference comparisons still pass.

## 4. Fixed after the audit

### R1-48: texture data within the GPU budget

`ITextureSampler::textureData` is gone. `textureInfo` gives a texture's shape (per tile its size and the MIP levels the file stores, from the headers), and `textureLevels` reads chosen levels of one tile a band of 64 rows at a time, converted to RGBA and to half per band (`core/texture/texel_stream.h`); a level the file does not store (a plain image read directly) is made with a box filter while its finest level is read once. `GpuRenderer` plans the budget over all textures the scene's materials sample before reading anything (`core/texture/texture_budget.h`) and copies each band into the CUDA array as it arrives, so host memory holds a band (and a row of sums), not every tile's every level as float RGBA. The `bad_alloc` fallback to the CPU in `Renderer` stays as a safety net.

Budget policy (docs/design/M10.md, G7): everything fits, everything is kept (device data and images bit-identical to before); otherwise every texture is capped at the largest power-of-two size that fits, and then, in order of first use, a reduced texture gets one level more where that still fits, all tiles of a UDIM set together. The old policy dropped levels per tile in upload order (first textures whole, later ones down to 1 x 1); a single texture keeps the same levels under both.

An independent review of the fix found three gaps, now closed: the plan counted the textures of every material, also those the device never uploads (VEX stand-ins, programs over the GPU's rows, whose textures were uploaded nonetheless; volume shaders over them), which could cap the others needlessly; plan and upload now share one rule (`forEachDeviceSampler` in `core/gpu/gpu_renderer.cpp`) and a program over the GPU's rows no longer uploads its textures. The default budget was measured at the first scene even without textures; now when the first texture loads. A changed `nova:gpuTextureBudget` waited for an unrelated edit and then read every texture again; now it is planned at the next pass and only the textures whose kept levels change are read again (device copies are freed per texture). Tests: "XPU plans only the textures it uploads", "XPU applies texture budget changes without a scene edit" [gpu] in tests/test_gpu_fixes.cpp.

A/B with nova_cli on Nova XPU (old and new build, same scenes): bit-identical where everything fits (a 2048^2 `.tx`, a 2 x 2 UDIM set, a plain EXR read directly, four mixed textures, 8 UDIM tiles of 8192^2) and for the 2048^2 `.tx` alone under 16, 4 and 1 MB; different by design for several textures or a UDIM set over the budget (uniform tiles, the cap) and for the plain EXR under 4 MB (now reduced; before it was uploaded whole regardless of the budget). Host memory for the 8 tiles of 8192^2 (5.3 GB on the device): peak working set 11.9 GB before, 0.50 GB after (a scene without textures: 0.42 GB).

## 6. Follow-up: exact light and shadow linking (R1-28, R1-31)

Both former limitations are removed (design in docs/design/M9.md, D15 and the M9.5 notes); CPU and XPU share the logic (`LightLinks` in core/lights/light_tree.h, `sampleShadowLinkedDome` in core/integrator/path.h).

- R1-28, light linking beyond 63 receiver sets. A light links to exactly one category, so "light i lights receiver set s" is "i lights everything, or s holds i's category". Per light the category's bit (all bits: unlinked), per receiver set its 64-bit category mask, per light-tree node the OR of its linked lights' bits plus a flag for an unlinked light below (`LightTreeNode::linksTo`): exact for any number of sets, with the same cost as the old bit test of a 64-set mask, so there is no second path. A subtree that holds no light of the receiver's set still has importance 0, so the tree's sampling and `pmf()` agree and nothing is wasted on rejections; selection by power keeps rejecting unlinked lights with the same probabilities in NEE and MIS. Receiver sets are `uint32_t` per instance and in the path state. The tree no longer depends on the receiver sets (new object categories replace the set table without a rebuild). Checks: the light tree's probabilities for 255 combinations are 0 for every light that does not light the set and sum to 1 over the others; a 16 x 16 grid of objects renders each object as the sum of its lights alone (mean relative error 0.2 %, worst cell 1.7 %, tree and power selection); through nova_cli and USD collections the same grid had a mean relative error of 404 % before (190 of 255 objects off by more than 5 %, the shared set 63) and 0.13 % after (none).
- R1-31, shadow-linked domes. A dome's light samples have no density where its distribution is 0 (an untextured dome everywhere; texels at or below the mean), and its BSDF samples rode on continuations, which every object stops. Now a shadow-linked dome's BSDF strategy is a shadow ray of its own at every non-delta event (surface hit, volume event, walk exit): along the continuation's direction, from where the event's light samples leave, with the dome's shadow category (the same occluders, fake-caustic transmittance and volumes as its light samples), MIS-weighted against them (`LightData::neeOnly()` is false for domes; continuations of non-delta events never collect shadow-linked lights). Both strategies see one visibility and keep their weights: unbiased wherever either has density. Delta continuations (mirrors) still collect shadow-linked lights with weight 1, every object occluding (documented in D15). One more shadow ray per non-delta event, only in scenes with a shadow-linked dome (XPU: shadow-ray kind 3, one more queue slot per path only then). Checks: with a black wall outside the dome's shadow set the ground renders as without the wall, and without the wall as with an unlinked dome, under MIS, LightOnly and BsdfOnly, untextured and textured, diffuse and rough metal; Karma's husk scene (`husk_lights`, dome shadow link excluding sphere A): next to A Karma 0.15540, Nova 0.12544 before, 0.15571 after.
- Review of this follow-up (low): a shadow-linked area light with sampling quality 0 lit nothing after non-delta events (light samples never pick it, BSDF rays skip NEE-only lights), so "NEE-only lights are unbiased because their light samples cover their whole emission" did not hold at selection weight 0; unlinked quality-0 lights, by contrast, still lit the scene through BSDF rays (R1-33). Karma CPU, measured with husk on the `husk_lights` scene: quality 0 turns a light's illumination off, rect light or dome, with or without a shadow link, mirrors included (C<RD><L> 0 everywhere, C<R[GS]><L> 0 in a mirror sphere against 0.673 at quality 1); quality 0.05 keeps the mean (0.29756 against 0.29777: a sample count); the camera still sees a camera-visible quality-0 light. Nova now does the same (`LightData::illuminates()`, D18): quality-0 lights are never chosen and no ray collects them, CPU and XPU; R1-33's outside-tree entry for them is gone. On that scene (nova_cli, 256 samples) C.*<L> of the unlinked quality-0 key was 0.29785 on A and 0.754 on the mirror sphere B before, 0 now; at quality 1 unchanged (0.29157 on A). Golden check after the merge with main: 34 scenes bit-identical. Every light that illuminates has a selection weight above 0, so NEE-only lights are unbiased. Checks: "Lights with sampling quality 0 light nothing" (replaces R1-33's test), "Sampling quality 0 turns a light's illumination off, shadow-linked or not" (a ground and a mirror sphere under a rect, a distant light with an angle and a dome: black at quality 0, linked or not), "XPU lights with sampling quality 0" (the same on the GPU), and `husk_lights` `key_quality0`, `key_quality0_shadow_excl_B` against Karma's 0.
- Golden check: all 33 reference scenes bit-identical (no reference scene uses linking).
- Performance (nova_cli, 960x540, 64 samples, minimum of 5 runs alternating with the pre-fix build on a shared, loaded machine; run-to-run spread about 5 %): `cornell_rect` +3.7 % CPU / +0.7 % XPU, `dome_sky` -4.4 % / -1.9 %, `instancer` +0.6 % / -3.3 %, 1000 sphere lights without linking +2.7 % / +3.4 %, the same with 64 light-link collections (66 receiver sets, past the old limit) +1.9 % / +2.0 %: no difference beyond the noise.
